# 🧬 添付ファイルの重複排除 {#attachment-deduplication}

[← Documentation Index に戻る](index.md)

## 📋 概要 {#overview}

メールの添付ファイルは、バイナリペイロードとしてデータベースに保存されます。**同じファイル**が多くのメールに添付されることは非常に頻繁にあります（署名内の会社ロゴ、転送されたPDF、ニュースレター、契約書など）。重複排除を行わない場合、各添付ファイルがそれらのバイトの独自のコピーを保持するため、膨大なデータベース容量を浪費します。

**添付ファイルの重複排除**は、すべての*一意な*ペイロードを、コンテンツアドレス指定テーブル（バイトの SHA-256 ハッシュをキーとする）に正確に一度だけ保存し、すべての同一の添付ファイルがその単一の共有コピーを参照できるようにします。これにより、添付ファイルが多いアーカイブのストレージフットプリントを大幅に削減できます。

## ⚙️ 仕組み {#how-it-works}

### 新しい添付ファイル {#new-attachments}
新しいメールがアーカイブされるたび（IMAP、Microsoft 365 / Graph、EML インポート、MBOX インポートなど）、添付ファイルペイロードはハッシュ化され、一度だけ保存されます。同じペイロードが既に存在する場合、新しい添付ファイルは既存のコンテンツ行を単に参照します。これはデータレイヤーで透過的に行われるため、すべてのアーカイブパスが自動的にカバーされます。

### 既存のデータ（移行） {#existing-data-migration}
この機能が導入される**前**にアーカイブされた添付ファイルを既に含むインストールについては、**堅牢で再開可能なバックグラウンド移行**が、既存のインラインペイロードを共有コンテンツ行に変換します。

- 添付ファイルを**バッチ単位**で処理し、各バッチは独自のトランザクション内で行われます。
- 進捗は専用の状態テーブルに保存されるため、移行は**アプリケーションの再起動後も継続**され、中断した箇所から単純に再開されます。
- **べき等（idempotent）**です。すでに移行された添付ファイルは、クラッシュや再起動の後であっても、二度と変更されることはありません。
- バックグラウンドで実行されるため、アプリケーションの通常の使用を妨げません。

移行が完了すると、次のような完了メッセージがログに記録されます。

```
Attachment Deduplication migration COMPLETED. 36199 attachments processed in 1.6 minutes.
```


次回の起動時には、実行すべき作業がないことが検出され、アイドル状態を維持します。もし重複排除されていない添付ファイルが残った場合（例えば、古いバックアップを復元した後など）、自動的に再開してそれらを移行します。システムは常に完全に重複排除された状態へと収束します。

### ガベージコレクション（常時実行） {#garbage-collection-always-on}
メール（およびしたがって添付ファイル）が削除されると、共有ペイロードが参照されなくなることがあります。組み込みのガベージコレクションが、これらの孤立したコンテンツ行を削除します。

> 🧹 **孤立したデータのクリーンアップは、`DatabaseMaintenance` 機能とは無関係に、常に実行されます。** 移行の直後に一度実行され、その後定期的に（毎回 `OrphanCleanupIntervalHours`、デフォルトは 12 h）実行されます。`DatabaseMaintenance__Enabled=true` のとき、同じクリーンアップが毎日の `VACUUM` の前にも追加で実行され、解放されたスペースが物理的に回収されます。

### 移行後のディスク使用量（重要） {#disk-usage-after-the-migration-important}

> 📈 **ダッシュボードの「Storage」の値は、移行の直後に一時的に上昇することがあります**（例: 3.5 GB → 5.3 GB）。これは想定された動作であり、バグではありません。
>
> ダッシュボードは**物理的な**データベースサイズ（`pg_database_size`）を報告します。移行がペイロードを共有ストレージに移動すると、古いインラインコピーは `NULL` に設定されますが、PostgreSQL (MVCC) はテーブルファイルが書き換えられるまで、それらの古いバイトを *dead tuples* として保持します。そのため、一瞬の間、データベースには古いコピーと新しいコピーの両方が含まれることになります。
>
> これを自動的に修正するために、アプリケーションは、**移行が完了し、かつ同期ジョブが実行されていない間に**、添付ファイルテーブルに対して**一度限りの** `VACUUM FULL` を実行します。これによりテーブルが書き換えられ、解放されたスペースがオペレーティングシステムに返されます。その後、報告されるサイズは元のサイズ**未満**に減少します。これは正確に一度だけ実行され（`ReclaimedAt` マーカーによって追跡）、再起動しても安全であり、同期が進行している間は延期されます（アイドル状態になると自動的にリトライします）。

>
> ⚠️ `VACUUM FULL` は実行中に添付ファイルテーブルをロックするため（その間、添付ファイルの読み取り/書き込みはできません）、書き換えのためにある程度の空きディスク容量を必要とします。代わりに手動で実行したい場合は、次を実行してください：
> ```sql
> VACUUM (FULL, ANALYZE) mail_archiver."EmailAttachments";
> ```

## 🔧 設定 {#configuration}

これらの設定はオプションです。デフォルト値はほとんどのインストールにおいて適切です。 [Setup Guide](Setup.md#-attachment-deduplication-settings) も参照してください。

| 設定 | デフォルト | 説明 |
|---------|---------|-------------|
| `AttachmentDeduplication__BatchSize` | `200` | 1つのトランザクションで移行される既存の添付ファイルの数。値が大きいほど移行は速くなりますが、バッチあたりのメモリ/DB負荷が増加します。 |
| `AttachmentDeduplication__DelayBetweenBatchesMs` | `0` | 負荷の高いシステムでDB負荷を抑制するための、移行バッチ間のオプションの休止時間 (ms)。 |
| `AttachmentDeduplication__StartupDelaySeconds` | `20` | 移行が開始されるまでのアプリ起動後の遅延 (s)（スキーマ移行を先に完了させるため）。 |
| `AttachmentDeduplication__OrphanCleanupIntervalHours` | `12` | 常時実行される孤立データガベージコレクションの間隔 (h)。 |
| `AttachmentDeduplication__CommandTimeoutSeconds` | `300` | 移行バッチ操作のデータベースコマンドタイムアウト（秒）。デフォルトは5分です。バッチがタイムアウトし続ける場合、サービスはバッチサイズを半分にして自動的にリトライします。 |

例 (`docker-compose.yml`):

```yaml
environment:
  - AttachmentDeduplication__BatchSize=200
  - AttachmentDeduplication__DelayBetweenBatchesMs=0
  - AttachmentDeduplication__StartupDelaySeconds=20
  - AttachmentDeduplication__OrphanCleanupIntervalHours=12
  - AttachmentDeduplication__CommandTimeoutSeconds=300
```

## ❓ FAQ {#faq}

**重複排除を無効にできますか？**
いいえ。これはコアとなるストレージ機能であり、常にアクティブです。上記のバッチサイズとスケジューリングパラメータを調整することのみ可能です。

**移行中のデータは安全ですか？**
はい。各バッチは単一のトランザクションであり、作業はべき等です。移行の途中でクラッシュまたは再起動が発生した場合、未完了のバッチはロールバックされ、次回の起動時に再処理されます。データが失われたり重複したりすることはありません。

**アーカイブが遅くなりますか？**
添付ファイルごとのハッシュ化のオーバーヘッドは無視できる程度です。既存データの一度限りの移行はバックグラウンドで実行され、必要に応じて `DelayBetweenBatchesMs` で制限できます。

**移行が同じカーソルでタイムアウトと再起動を繰り返します。どうすればよいですか？**
これは、非常に大規模なデータベース（数十万件のメール）において、200個の添付ファイルをSHA-256でハッシュ化する単一のバッチが、デフォルトのコマンドタイムアウトを超えてしまう場合に発生することがあります。現在、サービスはタイムアウトが発生すると、バッチサイズを半分にして自動的にリトライします。それでもタイムアウトが発生する場合は、手動でバッチサイズを下げたり、コマンドタイムアウトを増やしたりすることができます。

```yaml
environment:
  - AttachmentDeduplication__BatchSize=10
  - AttachmentDeduplication__CommandTimeoutSeconds=600
```

**どれくらいのスペースが節約できますか？**
それは、アーカイブにどれだけの重複した添付ファイルが含まれているかによって完全に異なります。繰り返される署名、ロゴ、または転送されたファイルが多いアーカイブほど、大きな恩恵を受けられます。
