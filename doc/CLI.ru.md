# 🖥️ CLI Commands {#cli-commands}

[← Назад к индексу документации](index.md)

## 📋 Обзор {#overview}

Некоторые задачи не предназначены для веб-интерфейса: например, импорт существующего архива из локальной файловой системы или перемещение сохраненных оригинальных сообщений между бэкендами хранения. Mail Archiver принимает обе эти операции в качестве команд в командной строке.

| Команда | Назначение |
|----------|---------|
| `--import-mbox` | Импорт MBox файла из смонтированного каталога |
| `--import-eml` | Импорт ZIP-архива с EML файлами из смонтированного каталога |
| `--migrate-raw-storage` | Перемещение сохраненных оригинальных сообщений между базой данных и файловой системой |

Все команды обрабатываются до запуска веб-конвейера и завершаются по окончании работы, поэтому их безопасно запускать вместе с `docker compose exec`, пока архив работает.

## ⚠️ Модель безопасности {#security-model}

Команды импорта доступны **только через CLI** — веб-интерфейса для просмотра или импорта локальных файлов не существует. Для их запуска вам необходим доступ к хосту Docker (`docker exec`).

**Белый список путей** (`LocalImport:AllowedPaths`) определяет, из каких директорий импортер может считывать данные. Файлы, находящиеся за пределами этих путей, отклоняются.

`--migrate-raw-storage` не подпадает под действие этого белого списка: он считывает только те файлы сообщений, которые сам архив записал в `RawMessages:FileSystem:BasePath`.

## 🛠️ Настройка {#setup}

### 1. Настройка разрешенных путей {#1-configure-allowed-paths}

В вашем `docker-compose.yml` установите разрешенные пути импорта:

```yaml
environment:
  - LocalImport__AllowedPaths__0=/data/import
  # Optional: multiple paths
  # - LocalImport__AllowedPaths__1=/data/import2
```

### 2. Монтирование файлов {#2-mount-your-files}

Примонтируйте директорию, содержащую ваши файлы MBox/EML, в контейнер:

```yaml
services:
  mailarchive-app:
    volumes:
      - /home/user/mbox-archives:/data/import
      - ./data-protection-keys:/app/DataProtection-Keys
```

Замените `/home/user/mbox-archives` на фактический путь на вашем Docker-хосте.

### 3. Перезапуск контейнера {#3-restart-the-container}

```bash
docker compose down && docker compose up -d
```

## 📝 Использование {#usage}

### Найдите ID целевого аккаунта {#find-your-target-account-id}

Перед импортом вам потребуется узнать ID базы данных целевого почтового аккаунта. Вы можете найти его через Web UI:

Перейдите в "Email Accounts", откройте сведения о целевом аккаунте; ID аккаунта отображается в списке аккаунтов или в URL при просмотре аккаунта.

### Импорт MBox файла {#import-an-mbox-file}

```bash
docker compose exec mailarchive-app dotnet MailArchiver.dll --import-mbox --file /data/import/myarchive.mbox --account-id 1 --folder INBOX
```

**Параметры:**
| Параметр | Обязательно | Описание |
|-----------|----------|-------------|
| `--import-mbox` | Да | Сигнализирует об операции импорта MBox |
| `--file <path>` | Да | Путь к MBox файлу внутри контейнера |
| `--account-id <id>` | Да | Database ID целевого почтового аккаунта |
| `--folder <name>` | Нет | Имя целевой папки (по умолчанию: `INBOX`) |

### Импорт EML файлов (ZIP архив) {#import-eml-files-zip-archive}

```bash
docker compose exec mailarchive-app dotnet MailArchiver.dll --import-eml --file /data/import/emails.zip --account-id 1
```

**Параметры:**
| Параметр | Обязательно | Описание |
|-----------|----------|-------------|
| `--import-eml` | Да | Сигнализирует об операции импорта EML |
| `--file <path>` | Да | Путь к **ZIP архиву**, содержащему `.eml` файлы, внутри контейнера |
| `--account-id <id>` | Да | Database ID целевого почтового аккаунта |

> **Важно:** `--import-eml` ожидает **ZIP архив**, содержащий `.eml` файлы — он **не** принимает отдельные `.eml` файлы. Чтобы импортировать одиночные EML файлы, сначала упакуйте их в ZIP архив:
> ```bash
> zip /data/import/emails.zip /data/import/*.eml
> ```
> 
> **Примечание для `dotnet run`:** При использовании `dotnet run` (вместо опубликованной DLL) отделяйте аргументы dotnet от аргументов приложения с помощью `--`:
> ```bash
> dotnet run -- --import-eml --file /data/import/emails.zip --account-id 1
> ```
> `--` сообщает `dotnet run`, что все последующие аргументы относятся к вашему приложению, а не к компилятору .NET.

## ⚙️ Справочник конфигурации {#configuration-reference}

| Переменная окружения | Значение по умолчанию | Описание |
|----------------------|-----------------------|-----------|
| `LocalImport__AllowedPaths__0` | `/data/import` | Первый разрешенный путь для локальных импортов |
| `LocalImport__AllowedPaths__1` | (пусто) | Второй разрешенный путь (опционально) |

Добавляйте больше путей, увеличивая индекс (`__2`, `__3` и т. д.).

## 🚫 Обработка ошибок {#error-handling}

| Ошибка | Причина | Решение |
|-------|-------|----------|
| `File not found` | Путь `--file` не существует в контейнере | Проверьте путь к файлу и монтирование тома |
| `File path is not in an allowed import directory` | Файл находится вне разрешенных путей | Переместите файл в разрешенный путь или добавьте его директорию в `LocalImport:AllowedPaths` |
| `Mail account with ID X not found` | Неверный ID аккаунта | Проверьте ID аккаунта через Web UI или запрос к базе данных |
| `Invalid account-id` | Нечисловое значение для `--account-id` | Используйте числовой ID базы данных |

## 🔒 Рекомендации по безопасности {#security-best-practices}

1. **Используйте монтирование только для чтения (read-only)**, когда это возможно:
   ```yaml
   volumes:
     - /home/user/mbox-archives:/data/import:ro
   ```

2. **Ограничивайте AllowedPaths** только теми директориями, которые вы действительно используете.

3. **Удаляйте монтирования томов** после завершения импорта, чтобы поддерживать чистоту поверхности безопасности.

4. **Никогда не открывайте доступ** к директории импорта через веб-сервер — для локального импорта не существует веб-эндпоинтов.

## 📦 Обзор форматов импорта {#import-formats-at-a-glance}

| CLI Flag | Input Format | Typical File Extension | Single Email | Bulk |
|----------|-------------|----------------------|--------------|------|
| `--import-mbox` | MBox file | `.mbox`, `.mbx` | ❌ (всегда bulk) | ✅ |
| `--import-eml` | ZIP archive of EMLs | `.zip` | ❌ (требуется ZIP) | ✅ |
| `--migrate-raw-storage` | Stored original messages | — | — | ✅ |

*Одиночные файлы `.eml` не поддерживаются напрямую. Используйте `zip`, чтобы упаковать их, или импортируйте через [web upload](Import-EML-MBox.md).*

## 🔧 Команды обслуживания {#maintenance-commands}

### Перемещение сохраненных оригинальных сообщений {#moving-stored-original-messages}

Когда включен `RawMessages:Enabled`, оригинальное сообщение каждого письма хранится либо в базе данных, либо в файлах, в зависимости от `RawMessages:Storage`. Эта команда перемещает уже сохраненные оригиналы из одного бэкенда в другой; настройки см. в [Original Message Storage](RawMessages.md#storage-backend).

```bash
# database -> filesystem
docker compose exec mailarchiver dotnet MailArchiver.dll \
  --migrate-raw-storage --from postgres --to filesystem

# filesystem -> database
docker compose exec mailarchiver dotnet MailArchiver.dll \
  --migrate-raw-storage --from filesystem --to postgres
```

| Аргумент | По умолчанию | Описание |
|----------|---------|-------------|
| `--from` | настроенный `RawMessages:Storage` | Бэкенд, из которого перемещаются сообщения. |
| `--to` | настроенный `RawMessages:Storage` | Бэкенд, в который перемещаются сообщения. |
| `--batch` | `200` | Количество сообщений на одну транзакцию базы данных. |

В отличие от команд импорта, эта команда не ограничена `LocalImport:AllowedPaths`: она считывает только те файлы сообщений, которые сам архив записал в `RawMessages:FileSystem:BasePath`.

**Что это гарантирует:**

- Перед копированием каждое сообщение проверяется на соответствие контрольной сумме, записанной в момент архивации. Сообщение, не прошедшее проверку, остается ровно там, где оно было, и об этом сообщается — поврежденный оригинал никогда не будет распространен, а его единственная оставшаяся копия никогда не будет удалена.
- Файл удаляется только после того, как транзакция базы данных, переместившая его, будет зафиксирована (commit), поэтому прерванный запуск не приведет к потере единственной копии.
- Запуск можно возобновить: работа выбирается на основе хранилища, записанного в каждом сообщении, поэтому повторный запуск команды продолжается с того места, где возникли незавершенные задачи.
- Одно плохое сообщение не прерывает выполнение всей операции. Код выхода будет `1`, если хотя бы одно сообщение не прошло проверку, и `0` в противном случае.

**Пример вывода:**

```text
Batch: 200 moved, 0 skipped, 0 failed
Batch: 200 moved, 0 skipped, 0 failed
Batch: 42 moved, 0 skipped, 1 failed
Done: 442 moved, 1 failed.
  Email 12345: checksum mismatch (recorded 4f1c..., file has 9ab2...)
```

Чтение всегда следует бэкенду, записанному в каждом сообщении, а не настроенному параметру, поэтому загрузка продолжает работать во время и после миграции. Изменение `RawMessages:Storage` влияет только на вновь архивируемую почту — запустите эту команду, чтобы переместить то, что уже сохранено.

> **Резервное копирование:** при использовании файлового бэкенда файлы сообщений находятся вне базы данных. Резервное копирование `RawMessages:FileSystem:BasePath` вместе с дампом базы данных обязательно; восстановление без файлов оставит оригиналы, которые невозможно будет предоставить.

## ❓ FAQ {#faq}

**В: Почему `--import-eml` требует ZIP-файл?**
О: Внутренний сервис импорта EML (`EmlImportService`) обрабатывает ZIP-архивы с помощью API `ZipFile` от .NET. Такая архитектура обеспечивает эффективный массовый импорт. Для отдельных файлов `.eml` упакуйте их в ZIP-архив (например, `zip emails.zip *.eml`) или воспользуйтесь [веб-загрузкой](Import-EML-MBox.md).

**В: Почему я не могу просматривать файлы через веб-интерфейс?**
О: Это осознанное проектное решение в целях безопасности. Данная функция намеренно реализована через CLI для взаимодействия на системном уровне, так как обычные пользователи не имеют прямого доступа к уровню ОС; они взаимодействуют только с Web UI.

Чтобы предотвратить такие риски безопасности, как атаки типа path traversal и несанкционированное раскрытие файловой системы, обычным пользователям разрешено использовать только Web UI для загрузки и импорта файлов. Это гарантирует, что они не смогут обойти предусмотренный интерфейс для доступа к файловой системе контейнера.
