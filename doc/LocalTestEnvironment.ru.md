# 🧪 Локальная тестовая среда {#local-test-environment}

[← Назад к индексу документации](index.md)

## 📋 Обзор {#overview}

В данном руководстве описывается, как запустить тестовый набор, приложение и IMAP-цель на машине разработчика. Оно предназначено для контрибьюторов: стек, который здесь разворачивается, намеренно небезопасен и не является руководством по развертыванию. Для развертывания см.
[Setup Guide](Setup.md).

Задействованы три компонента:

| Компонент | Предоставляется | Назначение |
|---|---|---|
| PostgreSQL | `docker-compose.test.yml` | Две базы данных: одна для `dotnet test`, другая для приложения |
| Dovecot | `docker-compose.test.yml` | IMAP-цель, заменяющая почтовый ящик mailcow |
| The application | `dotnet run` на хосте | Быстрее для итераций, чем пересборка образа контейнера |

## 🚀 Запуск стека {#starting-the-stack}

```bash
docker compose -f docker-compose.test.yml up -d
```

Это публикует всё только на loopback:

| Service | Host address | Notes |
|---|---|---|
| PostgreSQL | `127.0.0.1:5433` | 5433, а не 5432, чтобы не было конфликта с локальным сервером |
| Dovecot, plain | `127.0.0.1:1143` | Включена аутентификация в открытом виде |
| Dovecot, TLS | `127.0.0.1:1993` | Самоподписанный сертификат образа |

Чтобы остановить его и удалить все базы данных и сохраненную почту:

```bash
docker compose -f docker-compose.test.yml down -v
```

## 🗄️ Две базы данных {#the-two-databases}

Тестовый набор оставляет после себя фикстурные строки: после полного прогона в тестовой базе данных остается несколько десятков почтовых аккаунтов и пользователей. Если бы приложение использовало ту же базу данных, его фоновая синхронизация подхватила бы эти фикстуры и начала бы многократно пытаться связаться с несуществующими серверами. Поэтому контейнер postgres при первой инициализации создает две базы данных
(`tests/postgres/10-create-dev-db.sql`):

| Database | Used by | Configured in |
|---|---|---|
| `MailArchiver` | `dotnet test` | `tests/MailArchiver.Tests/appsettings.Test.json` |
| `MailArchiverDev` | `dotnet run` | `appsettings.Development.json` |

Оба конфигурационных файла добавлены в gitignore и должны быть созданы локально.

`tests/MailArchiver.Tests/appsettings.Test.json`:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=127.0.0.1;Port=5433;Database=MailArchiver;Username=mailuser;Password=masterkey"
  }
}
```

`appsettings.Development.json` в корне репозитория:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=127.0.0.1;Port=5433;Database=MailArchiverDev;Username=mailuser;Password=masterkey"
  },
  "DataProtection": { "KeyPath": "DataProtection-Keys" },
  "MailSync": { "IgnoreSelfSignedCert": true }
}
```

`DataProtection:KeyPath` имеет значение за пределами контейнера: по умолчанию используется абсолютный путь
`/app/DataProtection-Keys`, которого не существует на машине разработчика, и без него каждый
запрос завершается ошибкой при чтении связки ключей. `IgnoreSelfSignedCert` — это то, что позволяет приложению
принимать сертификат Dovecot на порту 1993.

## ✅ Запуск тестов {#running-the-tests}

```bash
dotnet test tests/MailArchiver.Tests/MailArchiver.Tests.csproj
```

Миграции применяются автоматически с помощью `TestDbFixture` при первом запуске. Большинству тестов вообще не требуется база данных; остальные используют PostgreSQL, поэтому они завершатся ошибкой с `Name or service not known`, если стек не запущен.

Строку подключения также можно передать через переменные окружения, что переопределит любой конфигурационный файл:

```bash
MailArchiverTest__ConnectionStrings__DefaultConnection="Host=...;Port=...;Database=...;Username=...;Password=..." \
  dotnet test tests/MailArchiver.Tests/MailArchiver.Tests.csproj
```

## 🖥️ Запуск приложения {#running-the-application}

```bash
ASPNETCORE_ENVIRONMENT=Development ASPNETCORE_URLS=http://127.0.0.1:5000 \
  dotnet run --project MailArchiver.csproj
```

`Properties/launchSettings.json` уже устанавливает `ASPNETCORE_ENVIRONMENT=Development` для
`dotnet run`, поэтому обычный `dotnet run --project MailArchiver.csproj` также работает и обслуживает
http://localhost:5179 (профиль `http`). `ASPNETCORE_URLS` выше вместо этого выбирает порт
контейнера 5000.

Ожидающие миграции применяются к `MailArchiverDev` при запуске. Войдите, используя учетные данные из `appsettings.json`
(`Authentication:Username` и `Authentication:Password`).

## 📬 Использование Dovecot target {#using-the-dovecot-target}

Dovecot принимает **любое имя пользователя** с паролем `pass`, поэтому для нового целевого почтового ящика не требуется предварительная настройка: просто выберите имя и войдите. Добавьте его в разделе Mail Accounts:

| Field | Plain | TLS |
|---|---|---|
| IMAP Server | `localhost` | `localhost` |
| IMAP Port | `1143` | `1993` |
| Use SSL | off | on |
| Username | anything, e.g. `offload-target@example.com` | same |
| Password | `pass` | same |

Конфигурация в `tests/dovecot/dovecot.conf` смоделирована на основе стандартных настроек самого образа, но с тремя намеренными отличиями, которые заставляют его вести себя как target в mailcow:

- **Maildir storage** вместо sdbox, используемого в образе, что соответствует тому, что использует mailcow.
- **`separator = /`**, как в mailcow. Пути к папкам разделяются по `/` и `\`, когда восстановление воссоздает иерархию папок, поэтому сервер, использующий `.`, вел бы себя иначе.
- **Специальные папки `Drafts`, `Junk`, `Sent` и `Trash` созданы заранее**, так как mailcow создает их автоматически. Это важно при тестировании миграции из Exchange: исходная папка с именем `Sent Items` окажется рядом с существующей `Sent`, а не объединится с ней, и именно с такой ситуацией приходится иметь дело при переименовании папок.

Аутентификация в открытом виде (plaintext) включена на порту 1143, так как приложение подключается без какой-либо транспортной защиты, если для учетной записи отключен SSL.

## 🌱 Наполнение архива для тестирования {#seeding-an-archive-to-test-against}

Пустой архив малополезен для тестирования восстановления или миграции, поэтому
`tests/seed/seed.sh` создает его:

```bash
# once, so the schema exists
ASPNETCORE_ENVIRONMENT=Development ASPNETCORE_URLS=http://127.0.0.1:5000 \
  dotnet run --project MailArchiver.csproj

tests/seed/seed.sh            # seed
tests/seed/seed.sh --reset    # discard what was seeded before, then seed again
```

Он создает две учетные записи, импортирует фикстуры и выводит список загруженных данных. Обе учетные записи
создаются с интервалом синхронизации один год для каждой, а источник дополнительно отключен,
чтобы фоновый сервис синхронизации его игнорировал: его сервера не существует, а в целевой Dovecot
нужно только добавлять данные. Одно предостережение: состояние планировщика хранится в памяти, поэтому
каждый перезапуск приложения планирует одну синхронизацию цели немедленно. Таким образом, цель также
исключает специальные папки Dovecot (`INBOX`, `Drafts`, `Junk`, `Sent`, `Trash`), чтобы при первой
синхронизации после перезапуска нечего было архивировать. Повторный запуск скрипта безвреден;
второй запуск сообщает, что все сообщения уже присутствуют.

Фикстуры находятся в `tests/seed/fixtures`, по одному mbox на каждую исходную папку, с
`manifest.tsv`, сопоставляющим каждый файл с его целевой папкой. Они импортируются через
собственный `--import-mbox` CLI приложения, и это сделано намеренно: CLI работает через
`MailImporter.ImportEmailToDatabase`, тот же импортер, который использует IMAP-синхронизация, поэтому строки попадают
ровно в том формате, в котором хранится реальный архив — адреса объединены с помощью `", "`, темы проходят через
`CleanText`, `SentDate` преобразуется в часовой пояс отображения, `RawHeaders` извлекается и усекается.
Вставка строк напрямую в базу данных позволила бы пропустить все эти этапы и привела бы к созданию фикстур,
которые незаметно отличаются от рабочих данных.

Каждое сообщение в фикстурах содержит заголовок `X-Fixture-Purpose`, объясняющий причину его существования, так что файлы
документируют сами себя:

```
X-Fixture-Purpose: ImapMailRestorer.cs:1196 refuses to emit this, so MimeKit invents a
  fresh random Message-Id on every append and the row duplicates each repetition
Subject: Message-ID without an at sign
Message-ID: <bare-token-no-at-sign>
```

Даты являются фиксированными, а не относительными текущего дня. Граница миграции (cutoff) преобразуется в
абсолютную дату перед запуском задания, поэтому фиксированный набор фикстур и фиксированная граница позволяют
тестировать одно и то же более предсказуемо, чем скользящие значения. Сообщения охватывают период с 2012 по 2026 год.

Структура папок имитирует почтовый ящик Exchange, и каждая папка создана для проверки определенного сценария:

| Source folder | Why it is there |
|---|---|
| `INBOX` | даты охватывают пятнадцать лет, плюс пограничные сообщения ниже |
| `Sent Items` | конфликтует с существующей специальной папкой `Sent` в целевом Dovecot |
| `Sent Items/2019` | переименование должно перезаписывать только начальный сегмент пути |
| `Sent Items Archive` | имеет общий префикс как подстрока, но не на границе сегмента, поэтому он не должен быть перезаписан |
| `Deleted Items` | исключение папки |
| `Deleted Items/Old` | исключение на родительской папке должно распространяться на потомков |
| `Junk E-Mail` | название папки в Exchange, которую Dovecot называет `Junk` |
| `Archive/Projects/2020` | три уровня вложенности |

Отдельные сообщения включают: сообщение без заголовка `Message-ID` (которому назначается детерминированный
запасной вариант), сообщение, у которого в `Message-ID` отсутствует `@` (которое не сохраняется при восстановлении в целости), тему,
содержащую управляющий символ, сообщение с цепочкой `Received` из трех переходов и сообщение без таковой,
несколько сообщений с двумя получателями `To`, а также две пары почти дублирующихся сообщений с разницей в одну секунду.

### Примечание о коде выхода {#a-note-on-the-exit-code}

`tests/seed/seed.sh` проверяет количество ошибок и некорректных данных в выводе импорта, а не
код выхода процесса. `MBoxImportService` сообщает о `CompletedWithErrors`, когда он пропускает
дубликаты, а CLI сопоставляет любой статус, кроме `Completed`, с выходом 1, поэтому повторный
запуск импорта завершается с ненулевым кодом, даже если ничего не пошло не так. Таким образом, повторный запуск скрипта наполнения безопасен
и сообщает, что все сообщения уже присутствуют.

## ⚠️ Не для продакшена {#not-for-production}

- Любой имя пользователя проходит аутентификацию в Dovecot с одним фиксированным паролем.
- Включена аутентификация в открытом виде (plaintext).
- Учетные данные базы данных соответствуют документированным значениям по умолчанию.
- Состояние почты и базы данных хранится в Docker volumes, которые `down -v` удаляет.

## 🔧 Устранение неполадок {#troubleshooting}

**Тесты завершаются ошибкой `Name or service not known`** — стек не запущен, или
отсутствует `appsettings.Test.json`, поэтому строка подключения переключается на значение по умолчанию в контейнере
`Host=postgres`.

**`NETSDK1226` при сборке** — неполные данные рабочей нагрузки в локальном .NET SDK, не связанные с этим
репозиторием. Либо запустите `dotnet workload repair`, либо соберите с помощью
`-p:AllowMissingPrunePackageData=true`.

**Dovecot перезапускается в цикле** — ошибка конфигурации. Команда `docker compose -f
docker-compose.test.yml logs dovecot` укажет на строку с ошибкой. Обратите внимание, что Dovecot не
принимает несколько настроек в одной строке внутри блока.

**Приложение возвращает HTTP 500 на каждый запрос** — обычно это связано с кольцом ключей защиты данных (data protection key ring).
Убедитесь, что `DataProtection:KeyPath` указывает на доступную для записи директорию.
