# 📤 释放（Date-Windowed Offload） {#date-windowed-offload}

[← 返回文档索引](index.md)

## 📋 概述 {#overview}

释放（Offload）会将晚于截止日期的存档邮件追加到另一个邮箱中，并将所有较旧的邮件保留在存档中。它适用于迁移场景：即新邮箱仅保留近期邮件，而完整的历史记录仍可通过 Mail Archiver 进行访问。

它与 [将所有电子邮件复制到另一个邮箱](MailboxMigration.md) 有五点不同：

| | 复制所有电子邮件 | 释放 (Offload) |
|---|---|---|
| 日期过滤器 | 无，全部或全无 | 截止日期，带有可选的上界 |
| 可重复执行 | 否，会再次追加所有内容 | 是，跳过目标端已有的内容 |
| 文件夹排除 | 否 | 是，可配置 |
| 文件夹重命名 | 否 | 是，可配置 |
| 预览 | 否 | 提供不写入数据的文件夹级干跑（dry run）报告 |

释放操作仅会对目标端进行追加。它永远不会删除存档中的内容，也永远不会触碰源邮箱。

## 🔁 重复运行是安全的 {#repeating-a-run-is-safe}

在第一次追加之前，整个目标邮箱会被建立索引，并且每条消息都会进行比对检查。因此，重复运行不会追加已经到达的消息，而是报告其已存在。这带来了三个实际结果：

- 中断的运行可以通过简单地再次运行来恢复。
- 完成的运行可以作为验证步骤重复执行。正确的运行结果是：没有追加任何内容，且所有内容均已存在。
- 在目标端被删除的消息会在下次运行时重新出现，因为它们已不在索引中。

有两个标准决定消息是否已存在，遵循以下顺序：

1. **Message-ID**，经过归一化处理。这完成了几乎所有的工作。
2. **指纹（Fingerprint）**，基于发件人、收件人、主题和发送时间（误差在两秒内）。这涵盖了那些存储的 Message-ID 缺失或格式错误的邮件。这类邮件无法使用原始 Message-ID 进行恢复，因此如果没有第二个标准，它们会在每次运行中都被视为重复。

任务会单独报告有多少匹配项来自指纹，因为这是可能静默失败的标准。

## ⚙️ 配置 {#configuration}

一个新的 `Offload` 部分，其默认值会重现之前的行为：

```json
"Offload": {
  "MaxConcurrentJobs": 1,
  "PrefetchMaxMessages": 500000,
  "ExcludedSourceFolders": [],
  "FolderRenameMap": {},
  "MarkAsSeen": true
}
```

| 键 (Key) | 默认值 | 用途 |
|---|---|---|
| `MaxConcurrentJobs` | `1` | 同时运行多少个恢复或释放任务。设置为 1 可保持任务队列始终具备的严格串行行为。无论此值如何，每个目标邮箱最多只能运行一个任务。 |
| `PrefetchMaxMessages` | `500000` | 目标邮箱中索引消息数量的上界。超过此值后，重复检查将缩小到单个文件夹并记录该操作。 |
| `ExcludedSourceFolders` | empty | 永不释放的源文件夹。在重命名之前进行匹配，并涵盖子文件夹。 |
| `FolderRenameMap` | empty | 重写源文件夹路径的前导段。 |
| `MarkAsSeen` | `true` | 追加的邮件是否标记为已读。 |

两个文件夹设置都特意留空。在未被要求的情况下重写或丢弃文件夹会令使用恢复路径的用户感到意外，因此不带配置的运行会迁移一切（包括垃圾邮件文件夹），并在目标端自身的特殊文件夹旁边创建第二套特殊文件夹。

### 文件夹排除与重命名 {#folder-exclusions-and-renaming}

对于 Exchange 到 Dovecot 的迁移，这两个设置通常如下所示：

```json
"ExcludedSourceFolders": ["Junk E-Mail", "Deleted Items"],
"FolderRenameMap": {
  "Sent Items": "Sent",
  "Deleted Items": "Trash",
  "Junk E-Mail": "Junk"
}
```

如果没有重命名映射，每个迁移后的邮箱都会同时拥有 `Sent` 和 `Sent Items`，因为 Dovecot 会预先创建自己的特殊用途文件夹。

关于这些设置的应用，有四点需要注意，因为每一点都可能导致意外：

1. **排除规则优先匹配** 源名称。如果先进行重命名，那么对 `Deleted Items` 的排除规则在它变为 `Trash` 后将永远不会触发。
2. **重命名会重写最长的匹配路径前缀**，在段边界处进行。`Sent Items` 变为 `Sent` 的同时也会使 `Sent Items/2019` 变为 `Sent/2019`，并保持 `Sent Items Archive` 不变。
3. **匹配不区分大小写**，且 `/` 和 `\` 都被视为分隔符。
4. **两个源文件夹可能会合并为一个目标文件夹**。`Sent Items` 和 `Sent` 同时变为 `Sent` 是正常的，不会导致目标文件夹被打开两次。

在两次运行之间更改重命名映射不会导致重复，因为重复检查是针对整个目标邮箱而非单个解析后的文件夹进行的。

## 🖥️ 通过界面运行 {#running-it-from-the-interface}

在账户详情页面，**释放到另一个邮箱 (Offload to Another Mailbox)** 会打开一个表单，包含目标邮箱、目标根文件夹、是否保留文件夹结构、日期窗口、干跑开关以及是否将追加的邮件标记为已读。配置好的排除项和重命名映射以只读方式显示，因此运行过程不会产生意外。

任务会被加入队列，其进度和按文件夹生成的报告会显示在任务状态页面和 **Jobs** 下。按文件夹生成的报告会列出源文件夹名称，因此仅对启动任务的用户和管理员可见。

目标邮箱可以是一个已禁用的 IMAP 账户（例如在正式上线前配置迁移目标）；如果目标不可达，运行会在连接时报错。Microsoft 365 账户不能作为释放目标；Graph 恢复路径保持不变。

### 谁可以运行 {#who-may-run-it}

管理员可以在任何两个账户之间进行释放。自我管理人员（Self-manager）**只能在分配给他们的账户之间**进行释放，包括两端：源端因为账户页面已经进行了范围限制，目标端因为目标列表被缩小到相同的集合，且在任务启动时会再次检查请求。因此，拥有单个分配账户的自我管理人员没有合格的目标，并会被告知这一点。

范围控制来自 `IAccountAccessResolver`，这是 REST API 和 MCP 服务器使用的同一个解析器，因此对于谁可以使用哪个邮箱只有一个定义。决策本身存在于 `OffloadTargetEligibility` 中，目标列表和请求检查都会调用它，因此表单提供的选项与服务器接受的内容不会出现偏差。

## ⌨️ 通过命令行运行 {#running-it-from-the-command-line}

```bash
docker compose exec mailarchive-app dotnet MailArchiver.dll \
  --offload --source-account-id 3 --target-account-id 7 \
  --since 2025-08-01 \
  [--until 2026-08-01] [--target-folder INBOX] \
  [--preserve-folders] [--dry-run] [--no-mark-seen]
```

| 参数 | 含义 |
|---|---|
| `--source-account-id` | 读取存档邮件的账户。必填。 |
| `--target-account-id` | 邮件追加到的 IMAP 账户。必填，且必须与源账户不同。 |
| `--since` | 发送日期的包含性下界，即 `YYYY-MM-DD`。必填。 |
| `--until` | 可选的包含性上界。 |
| `--target-folder` | 目标邮箱中的根文件夹。默认为 `INBOX`。 |
| `--preserve-folders` | 在根文件夹下重建源文件夹结构。 |
| `--dry-run` | 报告将会发生的操作，不进行实际追加。 |
| `--no-mark-seen` | 追加时不带 Seen 标记。 |

退出码：

| 代码 | 含义 |
|---|---|
| `0` | 所有内容均已追加或已存在。 |
| `1` | 至少有一条消息失败，或运行本身失败。 |
| `2` | 调用错误：参数错误或缺失、未知账户、目标不是 IMAP、源等于目标。 |

单次调用处理一个邮箱，这使得通过包含源、目标和截止日期的 CSV 文件可以实现大量邮箱的批量化脚本操作。

> **同时运行多个任务。** “每个目标一个任务”的规则仅存在于单个进程内，因此针对*同一个*目标邮箱的两个并发命令行调用可能会在另一个开始写入之前就各自获取了重复索引，从而导致两者都追加了相同的邮件。请划分工作量，确保每个并发调用都有不同的目标，这在 CSV 的每一行都是不同邮箱的情况下是常态。

## 🗓️ 截止日期是如何解释的 {#how-the-cutoff-is-interpreted}

- 过滤器是基于 **发送日期 (send date)**，而不是消息被存档的时间。存档时间戳是存档运行的时间，对于截止日期没有意义。
- 相对窗口（如“过去十二个月”）在**任务创建时会被解析为固定日期**。任务可能会运行很长时间并在之后重复执行，它必须每次都选择相同的邮件；存储的相对窗口会发生偏移。
- 截止日期按**配置的显示时区**进行解释（与搜索界面一致），下界包含该日期的 00:00。上界包含该整天。相对窗口（“过去 N 个月”）也会在对应的显示时区中解析，这与 `SentDate` 的存储方式一致。

### 已知限制 {#known-limitation}

- 当重复索引达到 `Offload:PrefetchMaxMessages` 时，范围会缩小并记录日志，而不是针对单个文件夹重试。索引构建器提供的 `restrictToFolder` 备选方案目前在释放路径中不被使用；提高限制是目前支持的解决方法。

## 📋 端到端迁移流程 {#a-migration-end-to-end}

1. 创建目标邮箱。对于大量创建，请参阅 [Account Import](Account-Import.md) 中的 CSV 批量导入。
2. 配置 `Offload:ExcludedSourceFolders` 和 `Offload:FolderRenameMap`。两者默认为空，跳过此步骤会迁移垃圾邮件文件夹并创建重复的特殊文件夹。
3. 在释放之前，确认每个源邮箱已完全存档。
4. **干跑一切。** 在写入任何内容之前，检查计数和解析后的目标文件夹名称。
5. 正式运行。从 `MaxConcurrentJobs` 等于 2 开始，并在观察目标服务器的处理情况后再提高数值；Dovecot 会限制每个用户和每个 IP 的并发连接数。
6. 重复运行以验证。预期结果是：没有追加任何内容，且所有内容均已存在。
7. 禁用源账户。

吞吐量受 `BatchOperation:PauseBetweenEmailsMs` 限制，默认为 50 毫秒，因此在计算服务器延迟之前，每秒最多允许二十次追加。

## 🔍 计数器含义 {#what-the-counters-mean}

| 计数器 | 含义 |
|---|---|
| Appended (已追加) | 已写入目标端。在干跑中，表示将会写入的数量。 |
| Already present (已存在) | 目标端已持有，通过任一标准判定。 |
| of those by fingerprint (其中通过指纹识别) | 有多少是通过第二个标准而非 Message-ID 识别的。 |
| Excluded folder (排除的文件夹) | 因源文件夹被排除而跳过。 |
| Failed (失败) | 无法追加。 |

如果重复索引未覆盖整个目标邮箱，则会报告警告，这发生在超过 `PrefetchMaxMessages` 或文件夹无法读取时。在这种状态下，重复运行可能会追加那些在未被索引部分中已存在的邮件。

## ⚠️ 注意事项与限制 {#notes-and-limits}

- 恢复的邮件现在携带其**原始投递时间**作为 IMAP 内部日期，该时间取自消息的 `Received` 链，若缺失则回退到发送日期。此前它携带的是存档运行的时间，这破坏了目标端的到达排序和基于年龄的规则。
- 由于重复运行会跳过已存在的内容，错误的内部日期无法通过重新运行来纠正：消息会被识别并跳过。请在正式运行前确保这一点正确，或者在目标端删除受影响的消息并重新运行。
- Microsoft 365 不支持作为释放目标。
- 重复检测只能识别它在目标邮箱中能看到的内容。通过其他路径到达目标端的邮件，仅在两个标准恰好匹配时才会被捕获。
