# 📧 Хранение оригинального сообщения {#original-message-storage}

[← Назад к индексу документации](index.md)

## 📋 Обзор {#overview}

По умолчанию архив сохраняет **распарсенные части** электронного письма: заголовки, текстовые и HTML-тела, вложения. Экспортируемый `.eml` восстанавливается на основе этих полей.

Этого достаточно для чтения письма, но это не сообщение **в том виде, в котором оно было получено**. Кодировки передачи, MIME-границы и свертывание заголовков (header folding) отличаются от оригинала, поэтому восстановленное сообщение больше не проходит проверку DKIM-подписи, а спам-сканеры оценивают его иначе.

При включенном хранении оригинального сообщения архив сохраняет сообщение целиком в том виде, в котором оно пришло, наряду с распарсенными полями. Хранимый оригинал — это то, что архив может доказать как доставленное сообщение.

| | Только распарсенные поля | С хранением оригинала |
| --- | --- | --- |
| Заголовки, тело, вложения | ✅ | ✅ |
| Побайтово точное сообщение | ❌ | ✅ |
| Проверка DKIM-подписи | ❌ | ✅ |
| Форензика (суд, аудит) | ограничено | ✅ |

## 🎯 Where the original is served {#where-the-original-is-served}

Once stored, the original is returned wherever a complete message is expected:

| Place | What happens |
| --- | --- |
| **Export EML** button on the email detail page | Serves the stored original when one exists, falls back to the reconstruction for emails archived without one. |
| **Restore to a mailbox** | Appends the stored original when one exists, falls back to the reconstruction for emails archived without one. |
| `GET /api/v1/emails/{id}/raw` | REST API download, see the [REST API guide](API.md#download-original-message). |
| `get_email_raw` | MCP tool, see the [MCP guide](MCP.md#get_email_raw). |

The response tells you which form you got, so a caller can tell a genuine original from
a reconstruction without inspecting the bytes:

| Signal | Meaning |
| --- | --- |
| `X-Raw-Message-Source: imap` | Exact copy from the IMAP server (`BODY[]` as delivered). |
| `X-Raw-Message-Source: graph` | Exact copy, the MIME content Exchange returned. |
| `X-Raw-Message-Source: eml-file` | Exact copy, the content of the imported `.eml` file. |
| `X-Raw-Message-Source: serialized` | Parsed message written back out. Identical except line endings are CRLF (MBox import, IMAP recovery fetch). |
| `X-Raw-Message-Sha256` | SHA-256 of the stored original. |
| `X-Raw-Message-Reconstructed: true` | No original stored; the message was rebuilt. No checksum header. |
| `X-Raw-Message-Storage` | Backend the original was read from (`postgres` or `filesystem`). |

The filename says it too: `email-{id}-original-...eml` for a stored original,
`email-{id}-...eml` for a reconstruction.

When a stored original **fails its checksum**, the export and the restore are refused
with an error message. Returning the reconstruction instead would hide that the archived
copy was altered, which is exactly what an archive must never do.

A restore reads the stored original and appends it through the provider's client, so the
mailbox receives the original headers and MIME structure. On IMAP the client serializes the
message again, so the exact byte stream is not guaranteed on the wire. On Microsoft 365 the
archived bytes travel unchanged, because Graph accepts the message in MIME form. The
archived copy itself is never modified.

## ⚙️ Settings {#settings}

Все настройки находятся в разделе `RawMessages` или задаются как переменные окружения с префиксом `RawMessages__`.

| Setting | Default | Description |
| --- | --- | --- |
| `RawMessages:Enabled` | `false` | Сохранять исходное сообщение каждого нового архивируемого письма. Письма, архивированные до включения этой настройки, не имеют исходного сообщения. |
| `RawMessages:MaxMessageSizeMb` | `50` | Сообщения размером более этого значения архивируются без исходного сообщения. `0` = без ограничений. |
| `RawMessages:IncludeGraph` | `true` | Также сохранять исходное сообщение для аккаунтов Microsoft 365 (Graph). Это требует одного дополнительного Graph-запроса на каждое сообщение, что расходует бюджет на ограничение частоты запросов (throttling). |
| `RawMessages:Storage` | `postgres` | Где хранятся байты сообщения: `postgres` (в базе данных) или `filesystem` (gzip-файл рядом с архивом). См. [Storage backend](#storage-backend). |
| `RawMessages:FileSystem:BasePath` | `RawMessages` | Директория, в которую записываются файлы сообщений, относительно корня контента приложения. Укажите на смонтированный том в Docker. |
| `RawMessages:FileSystem:ShardDepth` | `2` | Количество двухсимвольных уровней директорий, на которые распределяется id письма. `2` дает 10 000 директорий, `0` — плоская структура. Это позволяет поддерживать низкое количество файлов в каждой директории при больших архивах. |
| `RawMessages:FileSystem:VerifyChecksumOnRead` | `true` | Пересчитывать SHA-256 файла при каждой загрузке и сравнивать его с контрольной суммой, записанной в момент архивации. При несовпадении загрузка завершается ошибкой HTTP 500 вместо выдачи измененных байтов. |

### Sizing {#sizing}

Объем хранилища растет примерно на размер каждого письма, включая его вложения, в сжатом gzip виде. Вложения **не** дедуплицируются внутри сохраненного исходного сообщения, поэтому письмо с большим вложением занимает место этого вложения дважды: один раз в дедуплицированном хранилище вложений и один раз внутри исходного сообщения. Планируйте объем примерно в **два** раза больше размера базы данных архива без исходных сообщений.

Включение этой настройки не заполняет данными уже существующую почту. Только новые архивируемые письма получают исходное сообщение.

## 💾 Хранилище бэкенда {#storage-backend}

Настройка `Storage` определяет, где будут храниться байты. **Строка метаданных всегда остается в
базе данных**, какой бы бэкенд ни был настроен, и содержит SHA-256, размер, источник захвата и (для файлов) относительный путь. Эта строка позволяет архиву доказать, что должен содержать
сохраненное сообщение.

### postgres (по умолчанию) {#postgres-default}

Сжатое сообщение находится в колонке `Content` таблицы `mail_archiver."RawMessages"`.
Это поведение, которое всегда было у архива, и оно не требует дополнительного объема.

Выбирайте этот вариант, если база данных уже является вашей единицей резервного копирования и вы хотите иметь одну сущность для
бэкапа и восстановления.

### filesystem {#filesystem}

Сообщение записывается в `{BasePath}/{xx}/{yy}/{id}.eml.gz`, где `xx`/`yy` производятся
от email id. Строка в базе данных хранит только метаданные.

Выбирайте этот вариант, если архив достаточно велик, чтобы оригиналы доминировали в размере базы данных, или если вы хотите поместить файлы сообщений на более дешевое или отдельное хранилище.

!!! danger "Монтирование тома в Docker"
    По умолчанию `BasePath` (`RawMessages`) разрешается в `/app/RawMessages` **внутри
    контейнера**. Без bind mount этот каталог принадлежит записываемому слою контейнера, поэтому каждый пересозданный контейнер — включая `docker compose down && docker compose
    up -d`, обновление образа или перезагрузку хоста с эфемерным слоем — уносит с собой каждый сохраненный
    оригинал, в то время как строки базы данных выживают.

    Всегда монтируйте директорию на хост при использовании бэкенда filesystem:

    ```yaml
    services:
      mailarchive-app:
        volumes:
          - ./raw-messages:/app/RawMessages
    ```

    Путь на хосте (здесь `./raw-messages`) — это то, что вы резервное копируете. Путь в контейнере должен
    соответствовать `RawMessages:FileSystem:BasePath`, либо установите `RawMessages:FileSystem:BasePath` на
    выбранную вами точку монтирования. Если вы переместите точку монтирования, убедитесь, что `BasePath` указывает на нее:
    сохраненные значения `StoragePath` являются относительными, поэтому они продолжат разрешаться.

### Переключение бэкендов {#switching-backends}

Чтение следует хранилищу, записанному в каждой строке, а не настроенной настройке. После того как вы
измените `Storage`, сообщения, заархивированные ранее, по-прежнему будут доступны для скачивания оттуда, где они находятся.
Настройка влияет только на **новые** заархивированные письма.

Чтобы переместить то, что уже сохранено, запустите миграцию хранилища. См.
[CLI commands](CLI.md#moving-stored-original-messages) для получения полной справки:

```bash
# database -> filesystem
docker compose exec mailarchiver dotnet MailArchiver.dll \
  --migrate-raw-storage --from postgres --to filesystem

# filesystem -> database
docker compose exec mailarchiver dotnet MailArchiver.dll \
  --migrate-raw-storage --from filesystem --to postgres
```

Что гарантирует миграция:

- Каждое сообщение проверяется на соответствие записанной контрольной сумме перед копированием. Сообщение,
  которое не прошло проверку, остается на месте, и о нем сообщается: поврежденный оригинал никогда не распространяется и
  его единственная оставшаяся копия никогда не удаляется.
- Файл удаляется только после того, как транзакция базы данных, переместившая его, будет завершена (committed), так что
  прерванный запуск не может привести к потере единственной копии.
- Запуск можно возобновить. Работа выбирается по колонке `StorageType`, поэтому повторный запуск
  команды продолжается с того места, где работа еще не завершена.
- Код выхода будет `1`, если какое-либо сообщение не удалось обработать, и `0` в противном случае.

Миграция не требуется для работы архива. Она нужна только для переноса существующих
байт на другой бэкенд.

## 🛟 Резервное копирование и восстановление {#backup-and-restore}

=== "postgres backend"
    Ничего дополнительного. Оригиналы являются частью базы данных и охватываются обычным
    дампом, см. [Backup and Restore](BackupRestore.md).

=== "filesystem backend"
    Создавайте резервную копию директории `BasePath` **вместе с** дампом базы данных.

    Восстановление базы данных без файлов приведет к тому, что в архиве останутся строки,
    содержимое которых невозможно будет предоставить. В этом случае при попытке скачивания
    будет возвращена ошибка HTTP 404 вместо возврата некорректных данных, а сами письма
    останутся доступными для чтения через их обработанные поля.

## 🗑️ Удаление письма {#deleting-an-email}

Удаление письма удаляет и его оригинал: правила хранения (retention rules), ручное одиночное и массовое удаление, а также удаление целого почтового аккаунта — все это удаляет файл в рамках одной и той же операции. При использовании бэкенда `postgres` не требуется никаких дополнительных действий, так как байты передаются внутри строки, которую уже удаляет каскадная операция.

Файл удаляется **после** того, как строка письма зафиксирована (committed), но никогда не раньше. Эти два шага не могут быть одной транзакцией, так как файл не является частью транзакции базы данных, поэтому один из них должен следовать вторым. Этот порядок является безопасным: удаление, которое завершилось ошибкой или откатилось (например, на заблокированной записи), оставляет оригинал нетронутым, а сбой между двумя шагами оставляет файл без строки, который затем будет перераспределен механизмом sweep, описанным ниже. Обратный порядок привел бы к уничтожению оригинала письма, которое все еще существует.

**Осиротевшие файлы собираются.** Все, что проскочило мимо, включая файлы, оставшиеся от удалений, произведенных до появления этой очистки, удаляется путем периодического сканирования (sweep) `BasePath`, которое сравнивает каждый файл со строками и удаляет те, на которые не ссылается ни одно письмо:

| Setting | Default | Meaning |
| --- | --- | --- |
| `RawMessages__FileSystem__OrphanCleanupEnabled` | `true` | Включить или выключить sweep |
| `RawMessages__FileSystem__OrphanCleanupIntervalHours` | `24` | Как часто он запускается |
| `RawMessages__FileSystem__OrphanCleanupGraceHours` | `24` | Файлы моложе этого возраста никогда не затрагиваются |
| `RawMessages__FileSystem__OrphanCleanupStartupDelaySeconds` | `300` | Задержка перед первым запуском, чтобы сначала завершилась ожидающая миграция хранилища |

Период ожидания (grace period) — это то, что делает sweep безопасным: импорт записывает файл перед тем, как зафиксировать строку, которая на него ссылается, и файл, записанный мгновение назад, не должен быть ошибочно принят за «сироту». Наполовину записанные `.tmp` файлы в результате прерванной записи собираются по тому же правилу. При использовании бэкенда `postgres` sweep ничего не делает и даже не обходит директорию.

## 🔍 Проверка архива {#verifying-an-archive}

Контрольная сумма, записанная в момент создания архива, делает возможной проверку.

- **При загрузке** (`VerifyChecksumOnRead=true`, по умолчанию) файл хешируется и
  сравнивается. При несовпадении загрузка отклоняется с ошибкой HTTP 500.
- **При миграции хранилища** каждое сообщение проверяется перед копированием,
  в обоих направлениях.

Поскольку строка метаданных находится в базе данных, а байты могут находиться на диске, сравнение контрольных сумм является единственным способом заметить, что файл был изменен вне приложения.

## ⚠️ Что нужно знать {#things-to-know}

- **Включение не заполняет данные задним числом.** Только письма, архивированные после переключения, получают оригинал.
- **Отсутствие оригинала регистрируется как ошибка.** Если захват отклонен (сообщение выше `MaxMessageSizeMb`, нет пригодного для использования захвата) или запись в настроенный бэкенд завершилась неудачей, в логе фиксируется ошибка с id письма и причиной. Письмо остается в архиве без оригинала; автоматического заполнения задним числом и повторных попыток не предусмотрено.
- **Страница с деталями помечает отсутствие оригинала.** При `RawMessages:Enabled` на странице с деталями над заголовками отображается уведомление. Оно запрашивает бэкенд хранения, поэтому файл в файловой системе, который исчез, также будет помечен. В списке писем нет значков для каждой строки; это заняло бы слишком много места в колонке статуса.
- **Реконструкция — это не само сообщение.** Для писем без сохраненного оригинала любой путь загрузки возвращает пересобранное сообщение и сообщает об этом через `X-Raw-Message-Reconstructed: true`.
- **Файловая система означает два блока резервного копирования.** Базу данных и директорию сообщений необходимо восстанавливать вместе, иначе строки выживут без их содержимого.
- **`VerifyChecksumOnRead` потребляет ресурсы CPU.** При каждой загрузке большого сообщения выполняется декомпрессия и вычисление хеша. Не отключайте эту функцию, пока не измерите наличие проблемы; это единственная защита от скрытого изменения данных на диске.
- **Сохраненный оригинал не дедуплицируется.** Вложение, которое встречается во многих письмах, хранится один раз в хранилище вложений, но по одному разу в каждом письме внутри оригинала.
- **Удаление удаляет и оригинал тоже.** Письмо, удаленное по политике хранения или вручную, уносит с собой и свой сохраненный оригинал (файл и строку). Ничто не сохраняется, если архив больше не отображает это письмо.
