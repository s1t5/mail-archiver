# 📧 Original Message Storage {#original-message-storage}

[← Back to Documentation Index](index.md)

## 📋 Overview {#overview}

По умолчанию архив сохраняет **разобранные части** (parsed parts) электронного письма: заголовки, текстовое и HTML-тело, вложения. Экспортируемый `.eml` восстанавливается из этих полей.

Этого достаточно для чтения письма, но это не то же самое сообщение, **каким оно было получено**. Кодировки передачи (transfer encodings), MIME-границы и перенос строк в заголовках (header folding) отличаются от оригинала, поэтому восстановленное сообщение больше не проходит проверку DKIM-подписи, а спам-фильтры оценивают его иначе.

При включенном хранении оригинальных сообщений архив сохраняет сообщение целиком в том виде, в котором оно поступил, наряду с разобранными полями. Сохраненный оригинал — это то, что архив может доказать как фактически доставленное сообщение.

| | Только разобранные поля | С сохранением оригинала |
| --- | --- | --- |
| Заголовки, тело, вложения | ✅ | ✅ |
| Побайтово точное сообщение | ❌ | ✅ |
| Проверка DKIM-подписи | ❌ | ✅ |
| Форензика (суд, аудит) | ограничено | ✅ |

## 🎯 Где предоставляется оригинал {#where-the-original-is-served}

После сохранения оригинал возвращается везде, где ожидается полное сообщение:

| Место | Что происходит |
| --- | --- |
| Кнопка **Export EML** на странице с деталями письма | Предоставляет сохраненный оригинал, если он существует; в противном случае использует реконструкцию для писем, архивированных без оригинала. |
| **Restore to a mailbox** | Добавляет сохраненный оригинал, если он существует; в противном случае использует реконструкцию для писем, архивированных без оригинала. |
| `GET /api/v1/emails/{id}/raw` | Скачивание через REST API, см. [REST API guide](API.md#download-original-message). |
| `get_email_raw` | Инструмент MCP, см. [MCP guide](MCP.md#get_email_raw). |

Ответ сообщает, какую форму вы получили, поэтому вызывающая сторона может отличить подлинный оригинал от реконструкции без проверки байтов:

| Сигнал | Значение |
| --- | --- |
| `X-Raw-Message-Source: imap` | Точная копия с IMAP-сервера (`BODY[]` в том виде, в котором она была доставлена). |
| `X-Raw-Message-Source: graph` | Точная копия, MIME-содержимое, которое вернул Exchange. |
| `X-Raw-Message-Source: eml-file` | Точная копия, содержимое импортированного файла `.eml`. |
| `X-Raw-Message-Source: serialized` | Разобранное и повторно записанное сообщение. Идентично, за исключением того, что окончания строк — CRLF (импорт MBox, получение при восстановлении IMAP). |
| `X-Raw-Message-Sha256` | SHA-256 сохраненного оригинала. |
| `X-Raw-Message-Reconstructed: true` | Оригинал не сохранен; сообщение было пересобрано. Заголовок контрольной суммы отсутствует. |
| `X-Raw-Message-Storage` | Бэкенд, из которого был прочитан оригинал (`postgres` или `filesystem`). |

Имя файла также указывает на это: `email-{id}-original-...eml` для сохраненного оригинала,
`email-{id}-...eml` для реконструкции.

Если сохраненный оригинал **не проходит проверку контрольной суммы**, экспорт и восстановление отклоняются с сообщением об ошибке. Возврат реконструкции вместо оригинала скрыл бы тот факт, что архивная копия была изменена, а это именно то, чего архив никогда не должен допускать.

При восстановлении система считывает сохраненный оригинал и добавляет его через клиент провайдера, поэтому почтовый ящик получает оригинальные заголовки и MIME-структуру. Точный поток байтов при передаче не гарантируется, так как клиент сериализует сообщение заново; сама архивная копия остается неизменной.

## ⚙️ Настройки {#settings}

Все настройки находятся в разделе `RawMessages` или задаются как переменные окружения с префиксом `RawMessages__`.

| Настройка | По умолчанию | Описание |
| --- | --- | --- |
| `RawMessages:Enabled` | `false` | Сохранять оригинальное сообщение каждого нового архивируемого письма. Письма, архивированные до включения этой опции, не имеют оригинала. |
| `RawMessages:MaxMessageSizeMb` | `50` | Сообщения размером более этого значения архивируются без оригинала. `0` = без ограничений. |
| `RawMessages:IncludeGraph` | `true` | Также сохранять оригинал для учетных записей Microsoft 365 (Graph). Это требует одного дополнительного Graph-запроса на каждое сообщение, что расходует квоту на ограничение частоты запросов (throttling). |
| `RawMessages:Storage` | `postgres` | Где хранятся байты сообщения: `postgres` (в базе данных) или `filesystem` (gzip-файл рядом с архивом). См. [Storage backend](#storage-backend). |
| `RawMessages:FileSystem:BasePath` | `RawMessages` | Директория, в которую записываются файлы сообщений, относительно корневого каталога содержимого приложения. Укажите на смонтированный том в Docker. |
| `RawMessages:FileSystem:ShardDepth` | `2` | Количество двухсимвольных уровней директорий, на которые распределяется id письма. `2` дает 10 000 директорий, `0` — плоская структура. Это позволяет поддерживать низкое количество файлов в каждой директории в больших архивах. |
| `RawMessages:FileSystem:VerifyChecksumOnRead` | `true` | Пересчитывать SHA-256 файла при каждой загрузке и сравнивать его с контрольной суммой, записанной в момент архивации. При несовпадении загрузка завершается ошибкой HTTP 500 вместо выдачи измененных байтов. |

### Оценка объема {#sizing}

Объем хранилища растет примерно на размер каждого письма, включая вложения, в сжатом gzip виде. Вложения **не** дедуплицируются внутри сохраненного оригинала, поэтому письмо с большим вложением занимает место этого вложения дважды: один раз в дедуплицированном хранилище вложений и один раз внутри оригинала. Планируйте объем примерно в **два** раза больше размера базы данных архива без оригиналов.

Включение этой настройки не заполняет данными уже существующую почту. Оригинал получают только новые архивируемые письма.

## 💾 Хранилище (Storage backend) {#storage-backend}

Настройка `Storage` определяет, где будут храниться байты. **Строка метаданных всегда остается в
базе данных**, независимо от настроенного бэкенда, и содержит SHA-256, размер, источник захвата и (для файлов) относительный путь. Именно эта строка позволяет архиву доказать, что
должно содержать сохраненное сообщение.

### postgres (default) {#postgres-default}

Сжатое сообщение находится в колонке `Content` таблицы `mail_archiver."RawMessages"`.
Это поведение было у архива всегда, и оно не требует дополнительного объема.

Выбирайте этот вариант, если база данных уже является вашим модулем резервного копирования и вы хотите иметь одну сущность для
бэкапа и восстановления.

### filesystem {#filesystem}

Сообщение записывается в `{BasePath}/{xx}/{yy}/{id}.eml.gz`, где `xx`/`yy` выводятся
на основе id письма. Строка в базе данных хранит только метаданные.

Выбирайте этот вариант, если архив становится достаточно большим, что оригиналы начнут доминировать в размере базы данных, или если вы хотите поместить файлы сообщений на более дешевое или отдельное хранилище.

!!! danger "Монтирование тома в Docker"
    По умолчанию `BasePath` (`RawMessages`） указывает на `/app/RawMessages` **внутри
    контейнера**. Без bind mount этот каталог принадлежит записываемому слою контейнера, поэтому каждое пересоздание контейнера — включая `docker compose down && docker compose
    up -d`, обновление образа или перезагрузку хоста с эфемерным слоем — уносит с собой каждый сохраненный
    оригинал, в то время как строки в базе данных выживают.

    При использовании бэкенда filesystem всегда монтируйте каталог на хост:

    ```yaml
    services:
      mailarchive-app:
        volumes:
          - ./raw-messages:/app/RawMessages
    ```

    Путь на хосте (здесь `./raw-messages`) — это то, что вы делаете бэкапом. Путь в контейнере должен
    совпадать с `RawMessages:FileSystem:BasePath` или же установите `RawMessages:FileSystem:BasePath` на
    выбранную вами точку монтирования. Если вы переместите точку монтирования, убедитесь, что `BasePath` по-прежнему указывает на нее:
    сохраненные значения `StoragePath` являются относительными, поэтому они продолжат разрешаться.

### Переключение бэкендов {#switching-backends}

Чтение следует хранилищу, записанному в каждой строке, а не настроенной конфигурации. После того как вы
измените `Storage`, сообщения, заархивированные ранее, останутся доступными для скачивания из тех мест, где они находятся.
Настройка влияет только на **новые** заархивированные письма.

Чтобы переместить то, что уже сохранено, запустите миграцию хранилища. Полный справочник см. в
[CLI commands](CLI.md#moving-stored-original-messages):

```bash
# database -> filesystem
docker compose exec mailarchiver dotnet MailArchiver.dll \
  --migrate-raw-storage --from postgres --to filesystem

# filesystem -> database
docker compose exec mailarchiver dotnet MailArchiver.dll \
  --migrate-raw-storage --from filesystem --to postgres
```

Что гарантирует миграция:

- Каждое сообщение проверяется по записанной контрольной сумме перед копированием. Сообщение,
  которое не прошло проверку, остается на месте, и об этом сообщается: поврежденный оригинал никогда не распространяется, а
  его единственная оставшаяся копия никогда не удаляется.
- Файл удаляется только после того, как транзакция базы данных, переместившая его, была зафиксирована (committed), поэтому
  прерванный запуск не может привести к потере единственной копии.
- Процесс можно возобновить. Работа выбирается по колонке `StorageType`, поэтому повторный запуск
  команды продолжит выполнение с того места, где работа еще не завершена.
- Код выхода будет `1`, если какое-либо сообщение не удалось обработать, и `0` в противном случае.

Миграция не является обязательной для работы архива. Она нужна только для переноса существующих
байтов на другой бэкенд.

## 🛟 Резервное копирование и восстановление {#backup-and-restore}

=== "postgres backend"
    Ничего дополнительного. Оригиналы являются частью базы данных и охватываются обычным
    дампом, см. [Backup and Restore](BackupRestore.md).

=== "filesystem backend"
    Создавайте резервную копию директории `BasePath` **вместе с** дампом базы данных.

    Восстановление базы данных без файлов приведет к тому, что в архиве останутся строки,
    содержимое которых невозможно предоставить. В этом случае при загрузке будет возвращаться
    ошибка HTTP 404 вместо некорректных данных, а сами электронные письма останутся доступными
    для чтения через их разобранные поля.

## 🗑️ Удаление электронного письма {#deleting-an-email}

Удаление электронного письма удаляет и его оригинал: правила хранения (retention rules), ручное одиночное и массовое удаление, а также удаление учетной записи целиком — все это удаляет файл в рамках одной и той же операции. При использовании бэкенда `postgres` не требуется никаких дополнительных действий, так как байты находятся внутри строки, которую удаляет каскад.

Файл удаляется **после** того, как строка письма зафиксирована (committed), но никогда не до. Эти два шага не могут быть одной транзакцией, так как файл не является частью транзакции базы данных, поэтому один из них должен следовать за другим. Такой порядок является безопасным: если удаление завершится ошибкой или откатится (например, из-за заблокированной записи), оригинал останется нетронутым; если же произойдет сбой между двумя шагами, останется файл без соответствующей строки, который будет удален механизмом очистки (sweep), описанным ниже. Обратный порядок привел бы к уничтожению оригинала письма, которое все еще существует.

**Осиротевшие файлы собираются.** Все, что проскочило мимо, включая файлы, оставшиеся от удалений, совершенных до появления этой очистки, удаляется периодическим процессом `BasePath`, который сравнивает каждый файл со строками и удаляет те, на которые не ссылается ни одно письмо:

| Setting | Default | Meaning |
| --- | --- | --- |
| `RawMessages__FileSystem__OrphanCleanupEnabled` | `true` | Включить или выключить очистку |
| `RawMessages__FileSystem__OrphanCleanupIntervalHours` | `24` | Как часто запускается |
| `RawMessages__FileSystem__OrphanCleanupGraceHours` | `24` | Файлы моложе этого возраста никогда не затрагиваются |
| `RawMessages__FileSystem__OrphanCleanupStartupDelaySeconds` | `300` | Задержка перед первым запуском, чтобы завершилась ожидающая миграция хранилища |

Период ожидания (grace period) делает очистку безопасной: импорт записывает файл перед тем, как зафиксировать строку, указывающую на него, и файл, записанный мгновение назад, не должен быть ошибочно принят за «осиротевший». Наполовину записанные файлы `.tmp` в результате прерванной записи собираются по тому же правилу. При использовании бэкенда `postgres` очистка ничего не делает и даже не обходит директорию.

## 🔍 Проверка архива {#verifying-an-archive}

Контрольная сумма, записанная в момент создания архива, делает возможной проверку.

- **При загрузке** (`VerifyChecksumOnRead=true`, по умолчанию) файл хешируется и
  сравнивается. При несовпадении загрузка отклоняется с ошибкой HTTP 500.
- **При миграции хранилища** каждое сообщение проверяется перед копированием, в обоих
  направлениях.

Поскольку строка метаданных находится в базе данных, а байты могут находиться на диске, сравнение контрольных сумм — это единственный способ заметить, что файл был изменен вне приложения.

## ⚠️ Что нужно знать {#things-to-know}

- **Включение не заполняет данные задним числом.** Только письма, архивированные после переключения, получают оригинал.
- **Отсутствие оригинала регистрируется как ошибка.** Если захват отклонен (сообщение выше `MaxMessageSizeMb`, непригодный для захвата) или запись в настроенный бэкенд не удалась, в логе фиксируется ошибка с id письма и причиной. Письмо остается в архиве без оригинала; автоматического заполнения задним числом и повторных попыток не предусмотрено.
- **Интерфейс помечает отсутствие оригинала.** При использовании `RawMessages:Enabled` в списке писем отображается предупреждающий значок для каждого сообщения без сохраненного оригинала, а на странице с деталями отображается уведомление над заголовками. Список проверяет флаги одним запросом на страницу; страница деталей запрашивает бэкенд хранилища, поэтому файл в файловой системе, который исчез, также будет помечен.
- **Реконструкция — это не само сообщение.** Для писем без сохраненного оригинала любой путь загрузки возвращает реконструированное сообщение и сообщает об этом через `X-Raw-Message-Reconstructed: true`.
- **Файловая система подразумевает два блока резервного копирования.** База данных и директория сообщений должны восстанавливаться вместе, иначе строки выживут без своего содержимого.
- **`VerifyChecksumOnRead` потребляет ресурсы CPU.** При каждой загрузке большого сообщения оно декомпрессируется и хешируется. Не отключайте эту функцию, пока не измерите наличие проблемы; это единственная защита от скрытого изменения данных на диске.
- **Сохраненный оригинал не дедуплицируется.** Вложение, которое встречается во многих письмах, хранится один раз в хранилище вложений, но по одному разу для каждого письма внутри оригинала.
- **Удаление удаляет и оригинал тоже.** Письмо, удаленное по политике хранения или вручную, уносит с собой и сохраненный оригинал (файл и строку). Ничего не сохраняется, если архив больше не перечисляет это письмо.
