# 📧 Original Message Storage {#original-message-storage}

[← Back to Documentation Index](index.md)

## 📋 Overview {#overview}

По умолчанию архив сохраняет **разобранные части** (parsed parts) электронного письма: заголовки, текстовое и HTML-тело, вложения. Экспортируемый `.eml` восстанавливается на основе этих полей.

Этого достаточно для чтения письма, но это не сообщение **в том виде, в котором оно было получено**. Кодировки передачи (transfer encodings), MIME-границы и перенос строк в заголовках (header folding) отличаются от оригинала, поэтому восстановленное сообщение больше не проходит проверку DKIM-подписи, а спам-фильтры оценивают его иначе.

При включенном хранении оригинальных сообщений архив сохраняет сообщение целиком в том виде, в котором оно поступил, наряду с разобранными полями. Сохраненный оригинал — это то, что архив может доказать как фактически доставленное сообщение.

| | Только разобранные поля | С хранением оригинала |
| --- | --- | --- |
| Заголовки, тело, вложения | ✅ | ✅ |
| Побайтово точное сообщение | ❌ | ✅ |
| Проверка DKIM-подписи | ❌ | ✅ |
| Форензика (суд, аудит) | ограничено | ✅ |

## 🎯 Где выдается оригинал {#where-the-original-is-served}

После сохранения оригинал возвращается везде, где ожидается полное сообщение:

| Место | Что происходит |
| --- | --- |
| Кнопка **Export EML** на странице с деталями письма | Выдает сохраненный оригинал, если он существует; в противном случае использует реконструкцию для писем, архивированных без оригинала. |
| **Restore to a mailbox** | Добавляет сохраненный оригинал, если он существует; в противном случае использует реконструкцию для писем, архивированных без оригинала. |
| `GET /api/v1/emails/{id}/raw` | Скачивание через REST API, см. [REST API guide](API.md#download-original-message). |
| `get_email_raw` | Инструмент MCP, см. [MCP guide](MCP.md#get_email_raw). |

Ответ сообщает, какую форму вы получили, поэтому вызывающая сторона может отличить подлинный оригинал от реконструкции, не проверяя байты:

| Сигнал | Значение |
| --- | --- |
| `X-Raw-Message-Source: imap` | Точная копия с IMAP-сервера (`BODY[]` в том виде, в котором она была доставлена). |
| `X-Raw-Message-Source: graph` | Точная копия, MIME-содержимое, которое вернул Exchange. |
| `X-Raw-Message-Source: eml-file` | Точная копия, содержимое импортированного файла `.eml`. |
| `X-Raw-Message-Source: serialized` | Разобранное и повторно записанное сообщение. Идентично, за исключением того, что окончания строк — CRLF (импорт MBox, извлечение при восстановлении IMAP). |
| `X-Raw-Message-Sha256` | SHA-256 сохраненного оригинала. |
| `X-Raw-Message-Reconstructed: true` | Оригинал не сохранен; сообщение было пересобрано. Заголовок контрольной суммы отсутствует. |
| `X-Raw-Message-Storage` | Бэкенд, из которого был прочитан оригинал (`postgres` или `filesystem`). |

Имя файла также указывает на это: `email-{id}-original-...eml` для сохраненного оригинала,
`email-{id}-...eml` для реконструкции.

Если сохраненный оригинал **не проходит проверку контрольной суммы**, экспорт и восстановление отклоняются с сообщением об ошибке. Возврат реконструкции вместо оригинала скрыл бы тот факт, что архивная копия была изменена, а это именно то, чего архив никогда не должен допускать.

При восстановлении (restore) система считывает сохраненный оригинал и добавляет его через клиент провайдера, поэтому почтовый ящик получает оригинальные заголовки и MIME-структуру. Точный поток байтов при передаче не гарантируется, так как клиент сериализует сообщение заново; сама архивная копия остается неизменной.

## ⚙️ Настройки {#settings}

Все настройки находятся в разделе `RawMessages` или задаются как переменные окружения с префиксом `RawMessages__`.

| Настройка | Значение по умолчанию | Описание |
| --- | --- | --- |
| `RawMessages:Enabled` | `false` | Сохранять оригинальное сообщение каждого нового архивируемого письма. Для писем, архивированных до включения этой опции, оригинала не будет. |
| `RawMessages:MaxMessageSizeMb` | `50` | Сообщения размером более этого значения архивируются без оригинала. `0` = без ограничений. |
| `RawMessages:IncludeGraph` | `true` | Также сохранять оригинал для аккаунтов Microsoft 365 (Graph). Это требует одного дополнительного Graph-запроса на каждое сообщение, что расходует квоту на ограничение частоты запросов (throttling). |
| `RawMessages:Storage` | `postgres` | Где хранятся байты сообщения: `postgres` (в базе данных) или `filesystem` (gzip-файл рядом с архивом). См. [Storage backend](#storage-backend). |
| `RawMessages:FileSystem:BasePath` | `RawMessages` | Директория, в которую записываются файлы сообщений, относительно корня контента приложения. Укажите на смонтированный том в Docker. |
| `RawMessages:FileSystem:ShardDepth` | `2` | Количество двухсимвольных уровней директорий, на которые распределяется id письма. `2` дает 10 000 директорий, `0` — плоская структура. Это позволяет поддерживать низкое количество файлов в каждой директории при больших архивах. |
| `RawMessages:FileSystem:VerifyChecksumOnRead` | `true` | Пересчитывать SHA-256 файла при каждой загрузке и сравнивать его с контрольной суммой, записанной в момент архивации. При несовпадении загрузка завершится ошибкой HTTP 500 вместо выдачи измененных байтов. |

### Оценка объема {#sizing}

Объем хранилища растет примерно на размер каждого письма, включая вложения, в сжатом gzip виде. Вложения **не** дедуплицируются внутри сохраненного оригинала, поэтому письмо с большим вложением занимает место дважды: один раз в дедуплицированном хранилище вложений и один раз внутри оригинала. Планируйте объем примерно в **два** раза больше размера базы данных архива без оригиналов.

Включение этой настройки не заполняет данными уже существующую почту. Оригиналы получат только новые архивируемые письма.

## 💾 Хранилище (Storage backend) {#storage-backend}

Настройка `Storage` определяет, где будут храниться байты. **Строка метаданных всегда остается в
базе данных**, независимо от настроенного бэкенда, и содержит SHA-256, размер, источник захвата и (для файлов) относительный путь. Именно эта строка позволяет архиву подтвердить, что
должно содержать сохраненное сообщение.

### postgres (default) {#postgres-default}

Сжатое сообщение находится в столбце `Content` таблицы `mail_archiver."RawMessages"`.
Это поведение было у архива всегда, и оно не требует дополнительного объема.

Выбирайте этот вариант, если база данных уже является вашим модулем резервного копирования и вы хотите иметь одну сущность для
бэкапа и восстановления.

### filesystem {#filesystem}

Сообщение записывается в `{BasePath}/{xx}/{yy}/{id}.eml.gz`, где `xx`/`yy` выводятся
на основе id письма. Строка в базе данных хранит только метаданные.

Выбирайте этот вариант, если архив достаточно велик, и оригиналы будут доминировать в размере базы данных, или если вы хотите поместить файлы сообщений на более дешевое или отдельное хранилище.

!!! danger "Монтирование тома в Docker"
    По умолчанию `BasePath` (`RawMessages`） разрешается в `/app/RawMessages` **внутри
    контейнера**. Без bind mount этот каталог принадлежит записываемому слою контейнера, поэтому при каждом пересоздании контейнера — включая `docker compose down && docker compose
    up -d`, обновление образа или перезагрузку хоста с эфемерным слоем — все сохраненные
    оригиналы теряются, в то время как строки в базе данных выживают.

    При использовании бэкенда filesystem всегда монтируйте каталог на хост:

    ```yaml
    services:
      mailarchive-app:
        volumes:
          - ./raw-messages:/app/RawMessages
    ```

    Путь на хосте (здесь `./raw-messages`) — это то, что вы делаете бэкапом. Путь в контейнере должен
    совпадать с `RawMessages:FileSystem:BasePath` или `RawMessages:FileSystem:BasePath` должен быть установлен на
    выбранную вами точку монтирования. Если вы переместите точку монтирования, убедитесь, что `BasePath` по-прежнему указывает на нее:
    сохраненные значения `StoragePath` являются относительными, поэтому они продолжат разрешаться.

### Переключение бэкендов {#switching-backends}

Чтение следует хранилищу, записанному в каждой строке, а не настроенной параметру. После того как вы
измените `Storage`, сообщения, архивированные ранее, по-прежнему будут доступны для скачивания из тех мест, где они находятся.
Настройка влияет только на **новые** архивируемые письма.

Чтобы переместить уже сохраненные данные, запустите миграцию хранилища. Полный справочник см. в
[CLI commands](CLI.md#moving-stored-original-messages):

```bash
# database -> filesystem
docker compose exec mailarchiver dotnet MailArchiver.dll \
  --migrate-raw-storage --from postgres --to filesystem

# filesystem -> database
docker compose exec mailarchiver dotnet MailArchiver.dll \
  --migrate-raw-storage --from filesystem --to postgres
```

Что гарантирует миграция:

- Каждое сообщение проверяется по записанной контрольной сумме перед копированием. Сообщение,
  которое не прошло проверку, остается на месте, и об этом сообщается: поврежденный оригинал никогда не распространяется, а
  его единственная оставшаяся копия никогда не удаляется.
- Файл удаляется только после того, как транзакция базы данных, переместившая его, будет зафиксирована (committed), поэтому
  прерванный запуск не может привести к потере единственной копии.
- Процесс можно возобновить. Работа выбирается по столбцу `StorageType`, поэтому повторный запуск
  команды продолжит выполнение с того места, где работа еще не завершена.
- Код выхода `1`, если какое-либо сообщение не удалось обработать, `0` в противном случае.

Миграция не является обязательной для работы архива. Она нужна только для переноса существующих
байтов на другой бэкенд.

## 🛟 Резервное копирование и восстановление {#backup-and-restore}

=== "postgres backend"
    Ничего дополнительного. Оригиналы являются частью базы данных и охватываются обычным
    дампом, см. [Backup and Restore](BackupRestore.md).

=== "filesystem backend"
    Создавайте резервную копию директории `BasePath` **вместе с** дампом базы данных.

    Восстановление базы данных без файлов приведет к тому, что в архиве останутся строки,
    содержимое которых невозможно будет предоставить. В этом случае при попытке скачивания
    будет возвращаться ошибка HTTP 404 вместо некорректных данных, а сами электронные
    письма останутся доступными для чтения через их разобранные поля.

## 🗑️ Удаление электронного письма {#deleting-an-email}

Удаление электронного письма удаляет и его оригинал: правила хранения, ручное одиночное и массовое удаление, а также удаление учетной записи целиком — все это удаляет файл в рамках одной и той же операции. При использовании бэкенда `postgres` не требуется никаких дополнительных действий, так как байты находятся внутри строки, которую уже удаляет каскадное удаление.

Файл удаляется **после** того, как строка письма зафиксирована (committed), но никогда не раньше. Эти два шага не могут быть одной транзакцией, так как файл не является частью транзакции базы данных, поэтому один из них должен следовать вторым. Такой порядок является безопасным: удаление, которое завершилось ошибкой или откатилось (например, из-за заблокированной записи), оставляет оригинал нетронутым, а сбой между двумя шагами оставляет файл без соответствующей строки, который затем подбирается механизмом очистки (sweep), описанным ниже. Обратный порядок привел бы к уничтожению оригинала письма, которое все еще существует.

**Осиротевшие файлы собираются.** Все, что проскочило мимо, включая файлы, оставшиеся от удалений, совершенных до появления этой очистки, удаляется периодическим процессом `BasePath`, который сравнивает каждый файл со строками и удаляет те, на которые не ссылается ни одно письмо:

| Setting | Default | Meaning |
| --- | --- | --- |
| `RawMessages__FileSystem__OrphanCleanupEnabled` | `true` | Включить или выключить очистку |
| `RawMessages__FileSystem__OrphanCleanupIntervalHours` | `24` | Как часто она запускается |
| `RawMessages__FileSystem__OrphanCleanupGraceHours` | `24` | Файлы моложе этого возраста никогда не затрагиваются |
| `RawMessages__FileSystem__OrphanCleanupStartupDelaySeconds` | `300` | Задержка перед первым запуском, чтобы сначала завершилась ожидающая миграция хранилища |

Льготный период (grace period) — это то, что делает очистку безопасной: импорт записывает файл перед тем, как зафиксировать строку, которая на него указывает, и файл, записанный мгновение назад, не должен быть ошибочно принят за «осиротевший». Наполовину записанные файлы `.tmp` в результате прерванной записи собираются по тому же правилу. При использовании бэкенда `postgres` очистка ничего не делает и даже не обходит директорию.

## 🔍 Проверка архива {#verifying-an-archive}

Контрольная сумма, записанная в момент создания архива, делает возможной проверку.

- **При загрузке** (`VerifyChecksumOnRead=true`, по умолчанию) файл хешируется и
  сравнивается. При несовпадении загрузка отклоняется с ошибкой HTTP 500.
- **При миграции хранилища** каждое сообщение проверяется перед копированием
  в обоих направлениях.

Поскольку строка метаданных находится в базе данных, а байты могут находиться на диске, сравнение контрольных сумм — это единственный способ заметить, что файл был изменен вне приложения.

## ⚠️ Что нужно знать {#things-to-know}

- **Включение не выполняет ретроспективное заполнение.** Только письма, архивированные после переключения, получают оригинал.
- **Реконструкция — это не само сообщение.** Для электронных писем без сохраненного оригинала каждый путь загрузки возвращает реконструированное сообщение и сообщает об этом через `X-Raw-Message-Reconstructed: true`.
- **Файловая система означает два блока резервного копирования.** База данных и директория сообщений должны восстанавливаться вместе, иначе строки останутся без своего содержимого.
- **`VerifyChecksumOnRead` потребляет ресурсы CPU.** При каждой загрузке большого сообщения оно декомпрессируется и хешируется. Не отключайте эту функцию, пока не измерите наличие проблемы; это единственная защита от скрытого изменения данных на диске.
- **Сохраненный оригинал не дедуплицируется.** Вложение, которое встречается во многих письмах, хранится один раз в хранилище вложений, но по одному разу на каждое письмо внутри оригинала.
- **Удаление удаляет и оригинал тоже.** Письмо, удаленное по правилам хранения или вручную, забирает с собой свой сохраненный оригинал — и файл, и строку. Ничто не сохраняется, если архив больше не содержит это письмо в своем списке.
