# 📧 Original Message Storage {#original-message-storage}

[← Documentation Index に戻る](index.md)

## 📋 概要 {#overview}

デフォルトでは、アーカイブはメールの**解析済みパーツ**（ヘッダー、テキストおよびHTML本文、添付ファイル）を保持します。エクスポートされた `.eml` は、これらのフィールドから再構築されます。

これだけでメールを読むには十分ですが、**受信時そのまま**のメッセージではありません。転送エンコーディング、MIME境界、およびヘッダーの折り返しはオリジナルとは異なるため、再構築されたメッセージはDKIM署名の検証ができず、スパムスキャナーによるスコアリングも変わってしまいます。

original message storage を有効にすると、アーカイブは解析済みフィールドに加えて、到着した時の完全なメッセージを保持します。保存されたオリジナルこそが、アーカイブが「配信された」と証明できるものです。

| | 解析済みフィールドのみ | オリジナルを保存した場合 |
| --- | --- | --- |
| ヘッダー、本文、添付ファイル | ✅ | ✅ |
| バイト単位で正確なメッセージ | ❌ | ✅ |
| DKIM署名の検証 | ❌ | ✅ |
| フォレンジック用途（裁判、監査） | 限定的 | ✅ |

## 🎯 オリジナルが提供される場所 {#where-the-original-is-served}

保存されると、完全なメッセージが期待されるあらゆる場所でオリジナルが返されます。

| 場所 | 動作 |
| --- | --- |
| メール詳細ページの **Export EML** ボタン | オリジナルが存在する場合は保存されたオリジナルを提供し、オリジナルなしでアーカイブされたメールの場合は再構築版をフォールバックとして提供します。 |
| **Restore to a mailbox** | オリジナルが存在する場合は保存されたオリジナルを付加し、オリジナルなしでアーカイブされたメールの場合は再構築版をフォールバックとして提供します。 |
| `GET /api/v1/emails/{id}/raw` | REST API によるダウンロード、[REST API guide](API.md#download-original-message) を参照してください。 |
| `get_email_raw` | MCP ツール、[MCP guide](MCP.md#get_email_raw) を参照してください。 |

レスポンスにはどの形式を受け取ったかが示されるため、呼び出し側はバイトを検査することなく、本物のオリジナルと再構築版を判別できます。

| シグナル | 意味 |
| --- | --- |
| `X-Raw-Message-Source: imap` | IMAP サーバーからの正確なコピー (配信時の `BODY[]`)。 |
| `X-Raw-Message-Source: graph` | 正確なコピー、Exchange が返した MIME コンテンツ。 |
| `X-Raw-Message-Source: eml-file` | 正確なコピー、インポートされた `.eml` ファイルの内容。 |
| `X-Raw-Message-Source: serialized` | パースされたメッセージの書き出し。改行コードが CRLF である点を除いて同一 (MBox インポート、IMAP recovery fetch)。 |
| `X-Raw-Message-Sha256` | 保存されたオリジナルの SHA-256。 |
| `X-Raw-Message-Reconstructed: true` | オリジナルは保存されていません。メッセージは再構築されました。チェックサムヘッダーはありません。 |
| `X-Raw-Message-Storage` | オリジナルが読み取られたバックエンド (`postgres` または `filesystem`)。 |

ファイル名にもそれが示されます。保存されたオリジナルは `email-{id}-original-...eml`、再構築版は `email-{id}-...eml` です。

保存されたオリジナルが **チェックサムに失敗** した場合、エクスポートとリストアはエラーメッセージとともに拒否されます。代わりに再構築版を返してしまうと、アーカイブされたコピーが改ざんされたことを隠蔽することになり、これはアーカイブが絶対にやってはならないことです。

リストアは保存されたオリジナルを読み取り、プロバイダーのクライアントを通じてそれを付加するため、メールボックスにはオリジナルのヘッダーと MIME 構造が届きます。クライアントがメッセージを再度シリアル化するため、ネットワーク上での正確なバイトストリームは保証されませんが、アーカイブされたコピー自体は変更されません。

## ⚙️ 設定 {#settings}

すべての設定は `RawMessages` セクションにあるか、または `RawMessages__` プレフィックスを持つ環境変数として定義されます。

| 設定 | デフォルト | 説明 |
| --- | --- | --- |
| `RawMessages:Enabled` | `false` | 新たにアーカイブされたすべてのメールのオリジナルを保存します。この設定を有効にする前にアーカイブされたメールにはオリジナルがありません。 |
| `RawMessages:MaxMessageSizeMb` | `50` | これより大きいメッセージは、オリジナルなしでアーカイブされます。 `0` = 無制限。 |
| `RawMessages:IncludeGraph` | `true` | Microsoft 365 (Graph) アカウントでもオリジナルを保存します。メッセージごとに 1 つの追加 Graph リクエストが発生し、これはスロットリングの予算としてカウントされます。 |
| `RawMessages:Storage` | `postgres` | メッセージのバイトを保持する場所: `postgres` (データベース内) または `filesystem` (アーカイブの隣にある gzip ファイル)。 [Storage backend](#storage-backend) を参照してください。 |
| `RawMessages:FileSystem:BasePath` | `RawMessages` | メッセージファイルが書き込まれるディレクトリ（アプリケーションのコンテンツルートからの相対パス）。Docker では、これをマウントされたボリュームに指定してください。 |
| `RawMessages:FileSystem:ShardDepth` | `2` | メール ID が分散される 2 文字のディレクトリレベルの数。 `2` は 10,000 個のディレクトリを作成し、 `0` はフラットです。大規模なアーカイブにおいて、ディレクトリあたりのファイル数を低く抑えます。 |
| `RawMessages:FileSystem:VerifyChecksumOnRead` | `true` | ダウンロードのたびにファイルの SHA-256 を再計算し、アーカイブ時に記録されたチェックサムと比較します。不一致がある場合は、改ざんされたバイトを配信するのではなく、HTTP 500 でダウンロードを失敗させます。 |

### サイジング {#sizing}

ストレージのサイズは、gzip 圧縮された各メールとその添付ファイルの合計サイズとおよそ同等に増加します。添付ファイルは保存されたオリジナル内では重複排除**されません**。そのため、大きな添付ファイルを持つメールは、重複排除された添付ファイルストアとオリジナル内の 2 回分、その添付ファイルの容量を消費します。オリジナルなしのアーカイブのデータベースサイズの約 **2 倍**を見込んで計画してください。

この設定を有効にしても、既存のメールが遡って処理されることはありません。新しくアーカイブされるメールのみがオリジナルを取得します。

## 💾 Storage backend {#storage-backend}

`Storage` 設定により、バイトデータがどこに保存されるかが決まります。どのバックエンドが構成されていても、**メタデータ行は常にデータベース内に保持され**、SHA-256、サイズ、キャプチャソース、および（ファイルの場合は）相対パスを保持します。この行があることで、アーカイブは保存されたメッセージが何を含むべきかを証明できます。

### postgres (default) {#postgres-default}

圧縮されたメッセージは、`mail_archiver."RawMessages"` の `Content` カラムに保存されます。
これはアーカイブが従来から行ってきた動作であり、追加のボリュームを必要としません。

データベースがすでにバックアップユニットとして機能しており、バックアップとリストアの対象を一つにまとめたい場合にこれを選択してください。

### filesystem {#filesystem}

メッセージは `{BasePath}/{xx}/{yy}/{id}.eml.gz` に書き込まれ、そこでは `xx`/`yy` がメール ID から派生されます。データベースの行にはメタデータのみが保持されます。

アーカイブのサイズが非常に大きく、オリジナルデータがデータベースの容量を圧迫する場合や、メッセージファイルをより安価な、あるいは別のストレージに配置したい場合にこれを選択してください。

!!! danger "Docker でボリュームをマウントする"
    デフォルトの `BasePath` (`RawMessages`) は、**コンテナ内**の `/app/RawMessages` に解決されます。バインドマウントを行わない場合、そのディレクトリはコンテナの書き込み可能レイヤーに属することになります。そのため、`docker compose down && docker compose up -d` によるコンテナの再作成、イメージの更新、またはエフェメラルレイヤーを伴うホストの再起動が行われるたびに、データベースの行は生存し続ける一方で、保存されたすべてのオリジナルデータが失われてしまいます。

    filesystem バックエンドを使用する場合は、常にディレクトリをホストにマウントしてください：

    ```yaml
    services:
      mailarchive-app:
        volumes:
          - ./raw-messages:/app/RawMessages
    ```

    バックアップの対象となるのはホスト側のパス（ここでは `./raw-messages`）です。コンテナ側のパスは `RawMessages:FileSystem:BasePath` と一致させるか、あるいは `RawMessages:FileSystem:BasePath` を選択したマウントポイントに設定する必要があります。マウント先を移動した場合は、`BasePath` がそこを指すように維持してください。保存されている `StoragePath` の値は相対的なため、引き続き解決されます。

### Switching backends {#switching-backends}

読み取りは、設定された設定値ではなく、各行に記録されているストレージに従って行われます。`Storage` を変更した後でも、以前にアーカイブされたメッセージは、それらが保存されている場所から引き続きダウンロード可能です。この設定は、**新しく**アーカイブされるメールにのみ影響します。

既に保存されているデータを移動するには、ストレージ移行（storage migration）を実行してください。完全なリファレンスについては [CLI commands](CLI.md#moving-stored-original-messages) を参照してください：

```bash
# database -> filesystem
docker compose exec mailarchiver dotnet MailArchiver.dll \
  --migrate-raw-storage --from postgres --to filesystem

# filesystem -> database
docker compose exec mailarchiver dotnet MailArchiver.dll \
  --migrate-raw-storage --from filesystem --to postgres
```

移行が保証するもの：

- すべてのメッセージは、コピーされる前に記録されたチェックサムに対して検証されます。検証に失敗したメッセージは元の場所に残され、報告されます。破損したオリジナルが伝播されることはなく、その唯一のコピーが削除されることもありません。
- ファイルは、それを移動させたデータベースのトランザクションがコミットされた後にのみ削除されます。そのため、実行が中断されても唯一のコピーが失われることはありません。
- 実行は再開可能です。作業対象は `StorageType` カラムによって選択されるため、コマンドを再度開始すると、未完了の作業から継続されます。
- メッセージの失敗が1つでもある場合は終了コード `1`、それ以外の場合は `0` となります。

アーカイブを動作させるために移行は必須ではありません。移行は、既存のバイトデータを別のバックエンドに移動するためにのみ必要です。

## 🛟 バックアップと復元 {#backup-and-restore}

=== "postgres backend"
    追加の作業は不要です。オリジナルデータはデータベースの一部であり、通常の
    dumpによってカバーされます。詳細は [Backup and Restore](BackupRestore.md) を参照してください。

=== "filesystem backend"
    `BasePath` ディレクトリをデータベースのdumpと**一緒に**バックアップしてください。

    ファイルなしでデータベースを復元すると、アーカイブ内にコンテンツを配信できない
    行が残ってしまいます。その場合、ダウンロードは誤ったデータを返すのではなく
    HTTP 404 を返します。なお、メール自体は解析されたフィールドから読み取り可能です。

## 🗑️ メールの削除 {#deleting-an-email}

メールを削除すると、そのオリジナルも一緒に削除されます。保持ルール、手動による単一または一括削除、およびメールアカウント全体の削除は、すべて同じ操作の一部としてファイルを削除します。`postgres` バックエンドを使用している場合、追加で行うことはありません。なぜなら、バイトデータはカスケード削除によって既に削除される行の中に含まれているからです。

ファイルは、メールの行がコミットされた**後**に削除され、決してその前には削除されません。これら2つのステップを1つのトランザクションにすることはできません。ファイルはデータベースのトランザクションの一部ではないため、どちらかが後に行われる必要があるからです。この順序が安全な順序です。例えば、ロックされたレコードなどで削除が失敗またはロールバックした場合、オリジナルはそのまま残ります。また、2つのステップの間のクラッシュによってファイルが行なしで残ったとしても、後述のスイープによって回収されます。逆の順序では、まだ存在しているメールのオリジナルを破壊してしまいます。

**孤立したファイルは回収されます。** このクリーンアップ機能が存在する前に行われた削除によって残されたファイルを含め、漏れてしまったものはすべて、すべてのファイルを各行と比較して、どのメールからも参照されていないファイルを削除する `BasePath` の定期的なスイープによって削除されます。

| Setting | Default | Meaning |
| --- | --- | --- |
| `RawMessages__FileSystem__OrphanCleanupEnabled` | `true` | スイープの有効/無効を切り替えます |
| `RawMessages__FileSystem__OrphanCleanupIntervalHours` | `24` | 実行頻度 |
| `RawMessages__FileSystem__OrphanCleanupGraceHours` | `24` | これより新しいファイルは決して操作されません |
| `RawMessages__FileSystem__OrphanCleanupStartupDelaySeconds` | `300` | 初回実行までの遅延。これにより、保留中のストレージ移行が先に完了します |

猶予期間（grace period）があることで、スイープは安全になります。インポート処理は、それを指し示す行をコミットする前にファイルを書き込みます。数瞬前に書き込まれたファイルが孤立ファイルと誤認されてはなりません。中断された書き込みによる書き込み途中の `.tmp` ファイルも、同じルールに基づいて回収されます。`postgres` バックエンドでは、スイープは何もしませんし、ディレクトリを走査することさえありません。

## 🔍 アーカイブの検証 {#verifying-an-archive}

アーカイブ作成時に記録されたチェックサムによって、検証が可能になります。

- **ダウンロード時** (`VerifyChecksumOnRead=true`、デフォルト) ファイルのハッシュ値が計算され、比較されます。不一致の場合、HTTP 500 エラーとなりダウンロードが拒否されます。
- **ストレージ移行時** すべてのメッセージは、コピーされる前に（双方向において）検証されます。

メタデータ行はデータベースにあり、バイトデータはディスク上にある可能性があるため、チェックサムの比較は、アプリケーション外でファイルが変更されたことに気づくための唯一の方法です。

## ⚠️ 注意事項 {#things-to-know}

- **有効化してもバックフィルは行われません。** スイッチを切り替えた後にアーカイブされたメールのみ、オリジナルが取得されます。
- **オリジナルが欠落している場合はエラーとしてログに記録されます。** キャプチャが拒否された場合（上記の `MaxMessageSizeMb`、使用可能なキャプチャなし）、または設定されたバックエンドへの書き込みに失敗した場合、ログにはメール ID と理由を含むエラーが記録されます。メールはオリジナルなしでアーカイブに残ります。自動的なバックフィルやリトライは行われません。
- **再構築されたものはメッセージそのものではありません。** 保存されたオリジナルがないメールの場合、すべてのダウンロードパスは再構築されたメッセージを返し、`X-Raw-Message-Reconstructed: true` を通じてその旨を通知します。
- **Filesystem は2つのバックアップユニットを意味します。** データベースとメッセージディレクトリは、必ずセットでリストアする必要があります。そうしないと、コンテンツのない行だけが残ってしまいます。
- **`VerifyChecksumOnRead` は CPU コストがかかります。** 大容量メッセージをダウンロードするたびに、解凍とハッシュ計算が行われます。問題が確認されない限り、この設定は有効のままにしてください。これはディスク上でのサイレントな改ざんに対する唯一の保護手段です。
- **保存されたオリジナルは重複排除されません。** 多くのメールに登場する添付ファイルは、添付ファイルストアには1回だけ保存されますが、オリジナル内にはメールごとに1回ずつ保存されます。
- **削除するとオリジナルも削除されます。** 保存期間の設定または手動によって削除されたメールは、その保存されたオリジナル（ファイルと行の両方）も一緒に削除します。アーカイブにリストされていないものは何も保持されません。
