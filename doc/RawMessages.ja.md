# 📧 Original Message Storage {#original-message-storage}

[← Documentation Index に戻る](index.md)

## 📋 Overview {#overview}

デフォルトでは、アーカイブはメールの**解析済みパーツ**（ヘッダー、テキストおよびHTML本文、添付ファイル）を保持します。エクスポートされた `.eml` は、これらのフィールドから再構築されます。

これだけでメールを読むには十分ですが、**受信時そのまま**のメッセージではありません。転送エンコーディング、MIME境界、およびヘッダーの折り返し（header folding）はオリジナルとは異なるため、再構築されたメッセージはDKIM署名の検証ができなくなり、スパムスキャナーによるスコアも変わってしまいます。

Original message storage を有効にすると、アーカイブは解析済みフィールドと並行して、到着した時そのままの完全なメッセージを保持します。保存されたオリジナルこそが、アーカイブが「配信された」と証明できるものです。

| | 解析済みフィールドのみ | Original message storage 有効時 |
| --- | --- | --- |
| ヘッダー、本文、添付ファイル | ✅ | ✅ |
| バイト単位で正確なメッセージ | ❌ | ✅ |
| DKIM署名の検証 | ❌ | ✅ |
| フォレンジック用途（裁判、監査） | 限定的 | ✅ |

## 🎯 オリジナルの配信場所 {#where-the-original-is-served}

一度保存されると、完全なメッセージが期待されるあらゆる場所でオリジナルが返されます。

| 場所 | 発生する事象 |
| --- | --- |
| メール詳細ページの **Export EML** ボタン | オリジナルが存在する場合は保存されたオリジナルを配信し、存在しない状態でアーカイブされたメールの場合は再構築（reconstruction）にフォールバックします。 |
| **Restore to a mailbox** | オリジナルが存在する場合は保存されたオリジナルを付加し、存在しない状態でアーカイブされたメールの場合は再構築にフォールバックします。 |
| `GET /api/v1/emails/{id}/raw` | REST API によるダウンロード。詳細は [REST API guide](API.md#download-original-message) を参照してください。 |
| `get_email_raw` | MCP ツール。詳細は [MCP guide](MCP.md#get_email_raw) を参照してください。 |

レスポンスによって、どの形式を受け取ったかが通知されるため、呼び出し元はバイトを検査することなく、真正なオリジナルと再構築されたものを判別できます。

| シグナル | 意味 |
| --- | --- |
| `X-Raw-Message-Source: imap` | IMAP サーバーからの正確なコピー (`BODY[]` として配信されたもの)。 |
| `X-Raw-Message-Source: graph` | 正確なコピー、MIME コンテンツ Exchange が返したもの。 |
| `X-Raw-Message-Source: eml-file` | 正確なコピー、インポートされた `.eml` ファイルの内容。 |
| `X-Raw-Message-Source: serialized` | 解析後に書き出されたメッセージ。改行コードが CRLF である点を除いて同一 (MBox インポート、IMAP リカバリ フェッチ)。 |
| `X-Raw-Message-Sha256` | 保存されたオリジナルの SHA-256。 |
| `X-Raw-Message-Reconstructed: true` | オリジナルは保存されていません。メッセージは再構築されました。チェックサムヘッダーはありません。 |
| `X-Raw-Message-Storage` | オリジナルが読み取られたバックエンド (`postgres` または `filesystem`)。 |

ファイル名もそれを示しています。保存されたオリジナルには `email-{id}-original-...eml`、再構築されたものには `email-{id}-...eml` が付与されます。

保存されたオリジナルが **チェックサムに失敗した場合**、エクスポートおよびリストアはエラーメッセージとともに拒否されます。代わりに再構築されたものを返してしまうと、アーカイブされたコピーが改ざんされた事実を隠蔽することになりますが、これはアーカイブが絶対にやってはならないことです。

リストアでは保存されたオリジナルを読み取り、プロバイダーのクライアントを通じてそれを付加するため、メールボックスにはオリジナルのヘッダーと MIME 構造が届きます。IMAP ではクライアントがメッセージを再度シリアル化するため、ネットワーク上での正確なバイトストリームは保証されません。Microsoft 365 では、Graph が MIME 形式でメッセージを受け入れるため、アーカイブされたバイトは変更されずに転送されます。アーカイブされたコピー自体が変更されることは決してありません。

## ⚙️ 設定 {#settings}

すべての設定は `RawMessages` セクションに記述されるか、`RawMessages__` プレフィックスを持つ環境変数として定義されます。

| 設定 | デフォルト | 説明 |
| --- | --- | --- |
| `RawMessages:Enabled` | `false` | 新しくアーカイブされたすべてのメールのオリジナルを保存します。この設定を有効にする前にアーカイブされたメールにはオリジナルがありません。 |
| `RawMessages:MaxMessageSizeMb` | `50` | これより大きいメッセージは、オリジナルなしでアーカイブされます。`0` = 無制限。 |
| `RawMessages:IncludeGraph` | `true` | Microsoft 365 (Graph) アカウントについてもオリジナルを保存します。メッセージごとに 1 つ追加の Graph リクエストが発生し、これはスロットリングの予算にカウントされます。 |
| `RawMessages:Storage` | `postgres` | メッセージのバイトデータを保持する場所: `postgres` (データベース内) または `filesystem` (アーカイブの隣にある gzip ファイル)。[Storage backend](#storage-backend) を参照してください。 |
| `RawMessages:FileSystem:BasePath` | `RawMessages` | メッセージファイルが書き込まれるディレクトリ（アプリケーションのコンテンツルートからの相対パス）。Docker ではこれをマウントされたボリュームに指定してください。 |
| `RawMessages:FileSystem:ShardDepth` | `2` | メール ID が分散される 2 文字のディレクトリレベルの数。`2` は 10,000 個のディレクトリを作成し、`0` はフラットになります。大規模なアーカイブにおいて、ディレクトリごとのファイル数を低く抑えます。 |
| `RawMessages:FileSystem:VerifyChecksumOnRead` | `true` | ダウンロードのたびにファイルの SHA-256 を再計算し、アーカイブ時に記録されたチェックサムと比較します。不一致がある場合は、変更されたバイトを配信するのではなく、HTTP 500 でダウンロードを失敗させます。 |

### サイズ設計 {#sizing}

ストレージのサイズは、各メールのサイズ（gzip 圧縮された添付ファイルを含む）にほぼ比例して増加します。添付ファイルは保存されたオリジナル内では重複排除**されません**。そのため、大きな添付ファイルを持つメールは、重複排除された添付ファイルストアに 1 回、オリジナル内に 1 回の計 2 回、その添付ファイルのコストがかかります。オリジナルなしのアーカイブのデータベースサイズの約 **2 倍**を見込んで計画してください。

この設定を有効にしても、既存のメールが遡って処理されることはありません。新しくアーカイブされるメールのみがオリジナルを取得します。

## 💾 Storage backend {#storage-backend}

`Storage` 設定によって、バイトデータがどこに保存されるかが決まります。**メタデータ行は、どのバックエンドが構成されていても常にデータベース内に保持され**、SHA-256、サイズ、キャプチャソース、および（ファイルの場合は）相対パスを保持します。その行があることで、アーカイブは保存されたメッセージが何を含むべきかを証明できます。

### postgres (default) {#postgres-default}

圧縮されたメッセージは `mail_archiver."RawMessages"` の `Content` カラムに格納されます。
これはアーカイブが常に採用してきた動作であり、追加のボリュームを必要としません。

データベースがすでにバックアップの単位となっており、バックアップとリストアの対象を一つにまとめたい場合にこれを選択してください。

### filesystem {#filesystem}

メッセージは `{BasePath}/{xx}/{yy}/{id}.eml.gz` に書き込まれ、そこでは `xx`/`yy` がメール ID から派生されます。データベースの行にはメタデータのみが保持されます。

アーカイブが十分に大きく、オリジナルデータがデータベースのサイズを支配してしまう場合、またはメッセージファイルをより安価な、あるいは別のストレージに置きたい場合にこれを選択してください。

!!! danger "Docker でボリュームをマウントする"
    デフォルトの `BasePath` (`RawMessages`) は、**コンテナ内の** `/app/RawMessages` に解決されます。バインドマウントがない場合、そのディレクトリはコンテナの書き込み可能レイヤーに属するため、`docker compose down && docker compose up -d` によるコンテナの再作成、イメージの更新、またはエフェメラルレイヤーを伴うホストの再起動のたびに、データベースの行は生存する一方で、保存されたすべてのオリジナルが失われます。

    filesystem バックエンドを使用する場合は、常にディレクトリをホストにマウントしてください：

    ```yaml
    services:
      mailarchive-app:
        volumes:
          - ./raw-messages:/app/RawMessages
    ```

    ホストのパス（ここでは `./raw-messages`）がバックアップの対象です。コンテナのパスは `RawMessages:FileSystem:BasePath` と一致している必要があります。あるいは、選択したマウントポイントに `RawMessages:FileSystem:BasePath` を設定してください。マウント先を移動した場合は、`BasePath` がそれを指し続けるようにしてください。保存された `StoragePath` 値は相対的なため、解決し続けることができます。

### Switching backends {#switching-backends}

読み取りは、設定された設定ではなく、各行に記録されたストレージに従います。`Storage` を変更した後も、以前にアーカイブされたメッセージは、それらが存在する場所から引き続きダウンロード可能です。この設定は、**新しく**アーカイブされるメールにのみ影響します。

すでに保存されているものを移動するには、ストレージ移行を実行してください。完全なリファレンスについては [CLI commands](CLI.md#moving-stored-original-messages) を参照してください：

```bash
# database -> filesystem
docker compose exec mailarchiver dotnet MailArchiver.dll \
  --migrate-raw-storage --from postgres --to filesystem

# filesystem -> database
docker compose exec mailarchiver dotnet MailArchiver.dll \
  --migrate-raw-storage --from filesystem --to postgres
```

移行が保証すること：

- すべてのメッセージは、コピーされる前に記録されたチェックサムに対して検証されます。検証に失敗したメッセージはそのままの場所に残り、報告されます。破損したオリジナルが伝播されることはなく、唯一の残っているコピーが削除されることもありません。
- ファイルは、それを移動したデータベースのトランザクションがコミットされた後にのみ削除されます。そのため、実行が中断されても唯一のコピーが失われることはありません。
- 実行は再開可能です。作業は `StorageType` カラムによって選択されるため、コマンドを再度開始すると、未完了の作業から継続されます。
- いずれかのメッセージが失敗した場合は終了コード `1`、それ以外は `0` となります。

アーカイブを動作させるために移行は必須ではありません。移行は、既存のバイトを別のバックエンドに移動するためにのみ必要です。

## 🛟 バックアップと復元 {#backup-and-restore}

=== "postgres backend"
    追加の作業はありません。オリジナルはデータベースの一部であり、通常の
    dumpによってカバーされます。詳細は [Backup and Restore](BackupRestore.md) を参照してください。

=== "filesystem backend"
    `BasePath` ディレクトリをデータベースのdumpと**一緒に**バックアップしてください。

    ファイルなしでデータベースを復元すると、アーカイブには内容を配信できない
    行が残ることになります。その場合、ダウンロードは誤った内容を返すのではなく、
    HTTP 404 を返します。なお、メール自体は解析されたフィールドから読み取り可能な状態に
    保たれます。

## 🗑️ メールの削除 {#deleting-an-email}

メールを削除すると、そのオリジナルも一緒に削除されます。保持ルール、手動による単一および一括削除、そしてメールアカウント全体の削除はすべて、同じ操作の一部としてファイルを削除します。`postgres` バックエンドを使用している場合、追加で行うことは何もありません。なぜなら、バイト列はカスケードによって既に削除される行の中に含まれているからです。

ファイルは、メールの行がコミットされた**後**に削除され、決してその前ではありません。これら2つのステップを1つのトランザクションにすることはできません。なぜなら、ファイルはデータベースのトランザクションの一部ではないため、どちらか一方が後に行われる必要があるからです。この順序が安全な順序です。例えば、ロックされたレコードなどで削除が失敗またはロールバックした場合、オリジナルは未然に保護されます。また、2つのステップの間にクラッシュが発生した場合は、行のないファイルが残りますが、これは後述のスイープによって回収されます。逆の順序では、まだ存在するメールのオリジナルを破壊してしまうことになります。

**孤立したファイルは回収されます。** このクリーンアップが存在する前に行われた削除によって残されたファイルを含め、すり抜けてしまったものはすべて、すべてのファイルを各行と比較して、どのメールも参照していないファイルを削除する `BasePath` の定期的なスイープによって削除されます。

| 設定 | デフォルト | 意味 |
| --- | --- | --- |
| `RawMessages__FileSystem__OrphanCleanupEnabled` | `true` | スイープのオン/オフを切り替える |
| `RawMessages__FileSystem__OrphanCleanupIntervalHours` | `24` | 実行頻度 |
| `RawMessages__FileSystem__OrphanCleanupGraceHours` | `24` | これより新しいファイルには一切触れない |
| `RawMessages__FileSystem__OrphanCleanupStartupDelaySeconds` | `300` | 初回実行前の遅延（保留中のストレージ移行を先に完了させるため） |

猶予期間（grace period）があることで、スイープは安全になります。インポートは、それを指し示す行をコミットする前にファイルを書き込みます。そのため、数瞬前に書き込まれたファイルが孤立したファイルと誤認されてはなりません。中断された書き込みによる書き込み途中の `.tmp` ファイルも、同じルールに基づいて回収されます。`postgres` バックエンドでは、スイープは何もしませんし、ディレクトリを走査することさえありません。

## 🔍 アーカイブの検証 {#verifying-an-archive}

アーカイブ作成時に記録されたチェックサムによって、検証が可能になります。

- **ダウンロード時** (`VerifyChecksumOnRead=true`、デフォルト) ファイルのハッシュ値が計算され、比較されます。不一致がある場合は、HTTP 500 でダウンロードを拒否します。
- **ストレージ移行時** すべてのメッセージは、コピーされる前に（双方向で）検証されます。

メタデータ行はデータベースにあり、バイト列はディスク上にある可能性があるため、チェックサムの比較は、アプリケーション外でファイルが変更されたことを検知する唯一の方法です。

## ⚠️ 注意事項 {#things-to-know}

- **有効にしてもバックフィルは行われません。** スイッチを切り替えた後にアーカイブされたメールのみがオリジナルを持ちます。
- **オリジナルの欠落はエラーとしてログに記録されます。** キャプチャが拒否された場合（上記のメッセージ `MaxMessageSizeMb`、使用可能なキャプチャなし）、または設定されたバックエンドへの書き込みに失敗した場合、ログにはメール ID と理由を含むエラーが記録されます。メールはオリジナルがない状態でアーカイブに留まり、自動的なバックフィルやリトライは行われません。
- **詳細ページはオリジナルの欠落をフラグ立てします。** `RawMessages:Enabled` を使用すると、詳細ページのヘッダーの上に通知が表示されます。ストレージバックエンドに問い合わせを行うため、消失したファイルシステム上のファイルもフラグ立てされます。メールリストには行ごとのバッジはありません。ステータス列のスペースを占有しすぎるためです。
- **再構築されたものはメッセージそのものではありません。** 保存されたオリジナルがないメールの場合、すべてのダウンロードパスは再構築されたメッセージを返し、`X-Raw-Message-Reconstructed: true` を通じてその旨を伝えます。
- **ファイルシステムは2つのバックアップユニットを意味します。** データベースとメッセージディレクトリは一緒にリストアする必要があります。そうしないと、コンテンツのない行だけが残ってしまいます。
- **`VerifyChecksumOnRead` は CPU コストがかかります。** 大きなメッセージをダウンロードするたびに、解凍とハッシュ計算が行われます。問題が確認されない限り、これは有効にしたままにしてください。これはディスク上でのサイレントな改ざんに対する唯一の保護手段です。
- **保存されたオリジナルは重複排除されません。** 多くのメールに登場する添付ファイルは、添付ファイルストアには一度だけ保存されますが、オリジナル内ではメールごとに一度ずつ保存されます。
- **削除するとオリジナルも削除されます。** 保存期間の設定または手動によって削除されたメールは、ファイルと行の両方とともに、保存されたオリジナルも削除します。アーカイブにリストされていないものは何も保持されません。
