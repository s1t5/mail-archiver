# 📊 Rate Limit Handling {#rate-limit-handling}

[← Back to Documentation Index](index.md)

## 📋 概要 {#overview}

多くのメールプロバイダーは、IMAPアクセスに対して帯域幅制限を設けています。これらの制限は通常、24時間あたり数百メガバイトから数ギガバイトの範囲です。これらの制限を超える大規模なメールボックスを同期する場合、通常であれば同期プロセスは失敗するか、不完全なものとなります。

Mail Archiverには、これらの制限を自動的に管理する組み込みのレート制限ハンドリングシステムが含まれており、大規模なメールボックスであっても信頼性の高い同期を保証します。

## ⚙️ 仕組み {#how-it-works}

### 自動帯域幅トラッキング {#automatic-bandwidth-tracking}

システムは、IMAP同期中にダウンロードされるデータ量を継続的に監視します。設定された帯域幅制限に達すると、以下の動作が行われます：

1. **同期の自動一時停止**: 現在の同期操作が正常に停止します
2. **進捗の保存**: チェックポイントに同期が停止した正確な位置が保存されます
3. **ステータスの更新**: ダッシュボード上のアカウントに「Rate-Limited」ステータスが表示されます
4. **自動再開**: 制限がリセットされると（通常は24時間後）、保存されたチェックポイントから同期が再開されます

### 例: 14 GBのメールボックス、1日の制限が2.5 GBの場合 {#example-14-gb-mailbox-with-25-gb-daily-limit}

```
Day 1:  Sync starts → ~2.5 GB downloaded → Rate-Limited
        Status: Rate-Limited, Checkpoint saved

Day 2:  Limit still active → Sync skipped

Day 3:  Limit resets → Sync resumes from checkpoint
        → Additional ~2.5 GB → Rate-Limited again

Day 4-6: Continues...

Day N:   All 14 GB synced → Status: Completed
```

## 🔧 設定 {#configuration}

### 帯域幅トラッキングの有効化 {#enabling-bandwidth-tracking}

以下のセクションを `appsettings.json` に追加してください：

```json
{
  "BandwidthTracking": {
    "Enabled": true,
    "DailyLimitMb": 2500,
    "WarningThresholdPercent": 80,
    "PauseHoursOnLimit": 24
  }
}
```

### 設定オプション {#configuration-options}

| オプション | 説明 | デフォルト | 例 |
|--------|-------------|---------|---------|
| `Enabled` | 帯域幅トラッキングの有効/無効 | `false` | `true` |
| `DailyLimitMb` | 1日のダウンロード制限（メガバイト単位） | `2500` | `2500` |
| `WarningThresholdPercent` | ログに警告を表示する制限のパーセンテージ | `80` | `80` |
| `PauseHoursOnLimit` | 制限に達した際に一時停止する時間（時間単位） | `24` | `24` |

### 正しい制限値の設定 {#setting-the-correct-limit}

適切な `DailyLimitMb` の値を決定するには：

1. メールプロバイダーのドキュメントまたは利用規約を確認してください
2. IMAPの帯域幅制限またはダウンロードクォータを探してください
3. コーポレートメールシステムを使用している場合は、メール管理者にお問い合わせください
4. 不確かな場合は、控えめな値（例：2000 MB）から開始してください
5. 初回の同期中に、ログでレート制限の警告が出ていないか監視してください

## 👤 ユーザーエクスペリエンス {#user-experience}

### ダッシュボードのインジケーター {#dashboard-indicators}

レート制限が有効な場合、アカウントには以下が表示されます：

- **Status**: "Rate-Limited" 
- **Info Banner**: 状況と推定リセット時間が説明されます
- **Sync Progress**: 制限に達する前に処理されたメール数が表示されます

### 自動動作 {#automatic-behavior}

1. **手動操作は不要**: システムがすべてを自動的に処理します
2. **アプリケーションの再起動**: アプリケーションを再起動しても、レート制限の状態はデータベースに保持されます
3. **複数アカウント**: 各アカウントは個別に帯域幅をトラッキングします

### 保存される内容 {#what-gets-saved}

レート制限が発生すると、システムは以下を保存します：

- **同期チェックポイント**: 同期が停止した各フォルダ内の正確な位置
- **帯域幅使用量**: 当日の合計ダウンロードバイト数
- **制限ステータス**: 制限に達しているかどうか、およびいつリセットされるか

## 🗄️ データベースメンテナンス {#database-maintenance}

`DatabaseMaintenanceService` は古いデータを自動的にクリーンアップします：

- **帯域幅レコード**: 7日後に削除されます
- **同期チェックポイント**: 完了したチェックポイントは30日後に削除されます
- **未完了のチェックポイント**: 同期が完了するまで保持されます

## ✅ ベストプラクティス {#best-practices}

### 大規模なメールボックスの場合 {#for-large-mailboxes}

1. **帯域幅トラッキングを有効にする**: 1日の制限を超えるメールボックスには必須です
2. **初回同期の計画を立てる**: 大規模なメールボックスの完全な同期には数日かかる場合があります
3. **進捗を監視する**: ダッシュボードでレート制限のステータスを確認してください
4. **中断しない**: 自動再開機能に任せてください

### 管理者の場合 {#for-administrators}

1. **適切な制限を設定する**: `DailyLimitMb` をメールプロバイダーの実際の制限に合わせて設定してください
2. **ログを監視する**: 制限の80%に達すると警告メッセージが表示されます
3. **データベース容量**: 帯域幅トラッキングによる追加ストレージの使用量は最小限です
4. **変更前のバックアップ**: レート制限の設定を変更する前には、必ずバックアップを取ってください

### パフォーマンスに関する考慮事項 {#performance-considerations}

- ✅ **メモリへの影響**: 軽微 - バイト数を追跡するだけで、メール自体を保存するわけではありません
- ✅ **データベースへの影響**: 最小限 - 小さなレコードが自動的にクリーンアップされます
- ✅ **同期速度**: アクティブな同期中のパフォーマンスへの影響はありません

## 🛡️ 一時的な FETCH エラー / サーバー側のスロットリング {#transient-fetch-errors-server-side-throttling}

上述のバイトベースの帯域幅トラッキングに加えて、Mail Archiver は IMAP サーバー自体から通知される **メッセージごとのスロットリング** も検出し、対応します。一部のホスト型 IMAP プロバイダーは、アカウントごとまたは IP ごとのスロットリングを適用することがあります。これは、現在のセッション中の全体的なリクエスト量に基づいてサーバー側で強制されるため、**設定された `BatchOperation` の一時停止とは無関係** に発生します。

### 症状 {#symptoms}

サーバーが、メッセージボディに対する単一の `FETCH` コマンドに対して `NO` (または `BAD`) レスポンスを返し、以下のようなメッセージが含まれます：

- `NO Service temporarily unavailable`
- `NO Server unavailable, try again later`
- `NO [LIMIT] ...`
- `NO [OVERQUOTA] ...`
- `NO [UNAVAILABLE] ...`
- `NO [INUSE] ...`
- `throttle`、`rate limit` または同様のマーカーを含むレスポンス

認証、フォルダ一覧、およびメッセージ検索自体は通常成功しますが、実際のフルメッセージの取得のみが失敗します。

### 自動処理 {#automatic-handling}

このような一時的なエラーが検出されると、Mail Archiver はメッセージごとのリトライ戦略を適用します：

1. **指数バックオフによるリトライ**: 同じメッセージに対して最大 **3回のリトライ** を行い、遅延時間は **5 s → 15 s → 60 s** となります。
2. **接続の回復**: 各リトライの前に、接続、認証、およびフォルダ選択の状態が検証され、必要に応じて復元されます。
3. **成功時のリセット**: FETCH が成功すると、連続失敗カウンターがリセットされます。
4. **同期の正常な一時停止**: すべてのリトライ後も **10 メッセージ連続** で一時的なエラーが発生し続ける場合、現在の同期実行は正常に一時停止されます。これは帯域幅制限による一時停止と同じメカニズムを使用します：
   - `LastSync` タイムスタンプは更新され**ません**。
   - `BandwidthTracking` が有効な場合、チェックポイントが保持されるため、次の同期実行は最後に正常に処理されたメッセージから再開されます。
   - ジョブはレート制限中としてマークされます。
   - 次回のスケジュールされた同期で自動的に再開されます。

### 緩和策 {#mitigation}

サーバー側のスロットリングが頻繁に発生する場合は、`BatchOperation` 設定を調整してリクエストレートを下げてください：

```yaml
BatchOperation__BatchSize=10
BatchOperation__PauseBetweenEmailsMs=500
BatchOperation__PauseBetweenBatchesMs=5000
```

一部のプロバイダーは、秒あたりのレートではなく、**合計バイト数** または **時間枠あたりの合計 FETCH 数** に基づいてスロットリングを行うことに注意してください。その場合は：

- `BandwidthTracking` を有効にし（上記参照）、プロバイダーのドキュメントに記載されている制限に合わせて `DailyLimitMb` を設定してください。これにより、1日の割り当てを使い果たしたときに同期がクリーンに一時停止し、翌日に自動的に再開されます。
- 非常に大規模なメールボックスの初回同期には数日かかる場合がありますが、これは意図された動作です。

### 何が一時的なエラーとみなされるか {#what-counts-as-a-transient-error}

スロットリングに関連するテキストまたはレスポンスコードを含む IMAP `NO`/`BAD` レスポンスのみが一時的なものとして扱われます。その他のエラー（不正な形式のメッセージ、UTF-8 デコードの問題など）は、引き続き即座に `FailedEmails` としてカウントされ、リトライ/一時停止ロジックを**トリガーしません**。
