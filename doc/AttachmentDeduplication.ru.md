# 🧬 Дедупликация вложений {#attachment-deduplication}

[← Back to Documentation Index](index.md)

## 📋 Обзор {#overview}

Вложения в письмах хранятся в базе данных в виде бинарных полезных нагрузок (payloads). **Один и тот же файл** очень часто прикрепляется к множеству электронных писем (логотипы компаний в подписях, пересланные PDF, рассылки, контракты и т. д.). Без дедупликации каждое вложение хранит свою собственную приватную копию этих байтов, что приводит к огромным затратам дискового пространства базы данных.

**Дедупликация вложений** сохраняет каждую *уникальную* полезную нагрузку ровно один раз в таблице с адресацией по содержимому (ключом является SHA-256 хеш байтов) и позволяет всем идентичным вложениям ссылаться на эту единственную общую копию. Это значительно снижает объем хранилища для архивов с большим количеством вложений.

## ⚙️ Как это работает {#how-it-works}

### Новые вложения {#new-attachments}
Когда архивируется новое электронное письмо (IMAP, Microsoft 365 / Graph, импорт EML, импорт MBOX и т. д.), полезная нагрузка вложения хешируется и сохраняется один раз. Если такая же полезная нагрузка уже существует, новое вложение просто ссылается на существующую строку с контентом. Это происходит прозрачно на уровне данных, поэтому все пути архивации охвачены автоматически.

### Существующие данные (миграция) {#existing-data-migration}
Для установок, которые уже содержат вложения, архивированные **до** внедрения этой функции, предусмотрена **надежная, возобновляемая фоновая миграция**, которая преобразует существующие inline-данные в общие строки контента:

- Она обрабатывает вложения **пакетами (batch by batch)**, при этом каждый пакет обрабатывается в отдельной транзакции.
- Прогресс сохраняется в специальной таблице состояний, поэтому миграция **переживает перезапуск приложения** и просто продолжается с того места, где она остановилась.
- Она **идемпотентна** — уже мигрированные вложения больше никогда не затрагиваются, даже после сбоя или перезапуска.
- Она работает в фоновом режиме и не блокирует обычное использование приложения.

Когда миграция завершается, она записывает сообщение о завершении, например:

```
Attachment Deduplication migration COMPLETED. 36199 attachments processed in 1.6 minutes.
```

При следующем запуске система обнаружит, что делать больше нечего, и будет находиться в режиме ожидания. Если когда-либо останутся не дедуплицированные вложения (например, после восстановления старого бэкапа), система автоматически возобновит процесс и мигрирует их — система всегда стремится к состоянию полной дедупликации.

### Сборка мусора (всегда включена) {#garbage-collection-always-on}
Когда электронные письма (и, следовательно, вложения) удаляются, общая полезная нагрузка может остаться без ссылок. Встроенный сборщик мусора удаляет эти осиротевшие строки контента.

> 🧹 **Очистка сирот (orphan cleanup) ВСЕГДА работает**, независимо от функции
> `DatabaseMaintenance`. Она запускается один раз сразу после миграции, а затем периодически (каждые `OrphanCleanupIntervalHours`, по умолчанию 12 ч). При 
> `DatabaseMaintenance__Enabled=true`, эта же очистка дополнительно запускается перед ежедневным `VACUUM`, чтобы освободившееся место было физически возвращено системе.

### Использование диска после миграции (важно) {#disk-usage-after-the-migration-important}

> 📈 **Значение "Storage" на дашборде может кратковременно УВЕЛИЧИТЬСЯ сразу после
> миграции** (например, 3.5 ГБ → 5.3 ГБ). Это ожидаемое поведение, а не баг.
>
> Дашборд отображает **физический** размер базы данных (`pg_database_size`). Когда
> миграция перемещает полезную нагрузку в общее хранилище, она помечает старую inline-копию как `NULL`,
> но PostgreSQL (MVCC) хранит эти старые байты как *мертвые кортежи (dead tuples)* до тех пор, пока файл таблицы не будет
> перезаписан — поэтому на мгновение база данных содержит и старую, и новую копии.
>
> Чтобы исправить это автоматически, приложение выполняет **единоразовый**
> `VACUUM FULL` для таблицы вложений **после завершения миграции и в то время, когда не запущены задачи синхронизации**. Это перезаписывает таблицу и возвращает освободившееся место операционной системе; после этого сообщаемый размер становится **меньше** исходного. Операция выполняется ровно один раз (отслеживается с помощью маркера `ReclaimedAt`), безопасна при перезапусках и откладывается до тех пор, пока идет процесс синхронизации (автоматически повторяется после завершения ожидания).

>
> ⚠️ `VACUUM FULL` блокирует таблицу вложений на время выполнения операции (чтение/запись вложений в это время невозможны) и требует наличия свободного дискового пространства для перезаписи. Если вы хотите запустить её вручную, выполните:
> ```sql
> VACUUM (FULL, ANALYZE) mail_archiver."EmailAttachments";
> ```

## 🔧 Конфигурация {#configuration}

Эти настройки являются необязательными; значения по умолчанию оптимальны для большинства установок. См. также [Setup Guide](Setup.md#-attachment-deduplication-settings).

| Настройка | По умолчанию | Описание |
|---------|---------|-------------|
| `AttachmentDeduplication__BatchSize` | `200` | Количество существующих вложений, мигрируемых за одну транзакцию. Большие значения ускоряют миграцию, но увеличивают нагрузку на память/БД на каждый пакет. |
| `AttachmentDeduplication__DelayBetweenBatchesMs` | `0` | Необязательная пауза (мс) между пакетами миграции для ограничения нагрузки на БД в нагруженных системах. |
| `AttachmentDeduplication__StartupDelaySeconds` | `20` | Задержка (с) после запуска приложения перед началом миграции (чтобы сначала завершилась миграция схемы). |
| `AttachmentDeduplication__OrphanCleanupIntervalHours` | `12` | Интервал (ч) работы постоянно включенного сборщика мусора для осиротевших данных. |
| `AttachmentDeduplication__CommandTimeoutSeconds` | `300` | Таймаут команды базы данных (в секундах) для операций пакетов миграции. По умолчанию 5 минут. Если пакет все еще превышает таймаут, сервис автоматически пробует повторить операцию с уменьшенным размером пакета в два раза. |

Пример (`docker-compose.yml`):

```yaml
environment:
  - AttachmentDeduplication__BatchSize=200
  - AttachmentDeduplication__DelayBetweenBatchesMs=0
  - AttachmentDeduplication__StartupDelaySeconds=20
  - AttachmentDeduplication__OrphanCleanupIntervalHours=12
  - AttachmentDeduplication__CommandTimeoutSeconds=300
```

## ❓ FAQ {#faq}

**Можно ли отключить дедупликацию?**
Нет. Это базовая функция хранения, и она всегда активна. Вы можете только настраивать размер пакета и параметры расписания, указанные выше.

**Безопасны ли мои данные во время миграции?**
Да. Каждый пакет — это отдельная транзакция, и работа идемпотентна. Сбой или перезапуск во время миграции откатывает незавершенный пакет, и он будет повторно обработан при следующем запуске; данные не теряются и не дублируются.

**Замедляет ли это архивацию?**
Накладные расходы на хеширование каждого вложения ничтожны. Разовая миграция существующих данных выполняется в фоновом режиме и может быть ограничена с помощью `DelayBetweenBatchesMs`, если это необходимо.

**Миграция постоянно прерывается по таймауту и перезапускается на том же месте. Что мне делать?**
Это может происходить в очень больших базах данных (сотни тысяч писем), где один пакет из 200 вложений с хешированием SHA-256 превышает стандартный таймаут команды. Сервис теперь автоматически пробует повторить операцию с уменьшенным вдвое размером пакета при возникновении таймаута. Если вы все еще видите таймауты, вы можете вручную уменьшить размер пакета и/или увеличить таймаут команды:

```yaml
environment:
  - AttachmentDeduplication__BatchSize=10
  - AttachmentDeduplication__CommandTimeoutSeconds=600
```

**Сколько места я сэкономлю?**
Это полностью зависит от того, сколько дублирующихся вложений содержится в вашем архиве. Больше всего выигрывают архивы с большим количеством повторяющихся подписей, логотипов или пересланных файлов.
