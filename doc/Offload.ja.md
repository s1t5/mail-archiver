# 📤 Date-Windowed Offload {#date-windowed-offload}

[← Back to Documentation Index](index.md)

## 📋 Overview {#overview}

Offloadは、カットオフ（しきい値）より新しいアーカイブ済みメールを別のメールボックスに追記し、それより古いものはアーカイブ内に残します。これは、新しいメールボックスには直近のメールのみを保持させつつ、全履歴にはMail Archiverを通じてアクセスできるようにしたい移行（マイグレーション）のために存在します。

[Copy All Emails to Another Mailbox](MailboxMigration.md) とは5つの点で異なります：

| | Copy All Emails | Offload |
|---|---|---|
| Date filter | なし、すべて、または何もなし | カットオフ、オプションで上限指定が可能 |
| Repeatable | 不可、すべてを再度追記する | 可能、ターゲットが既に保持しているものはスキップする |
| Folder exclusions | なし | あり、設定可能 |
| Folder renaming | なし | あり、設定可能 |
| Preview | なし | 書き込みを行わずにフォルダごとのドライラン結果を報告 |

Offloadは常にターゲットへの追記のみを行います。アーカイブから削除することは決してありませんし、ソースメールボックスに触れることもありません。

## 🔁 Repeating a run is safe {#repeating-a-run-is-safe}

最初の追記の前に、ターゲットメールボックス全体がインデックス化され、すべてのメッセージがそれと照合されます。したがって、繰り返し実行しても、既に届いているものが追記されることはなく、代わりに「既に存在している」と報告されます。これには3つの実用的な結果があります：

- 中断された実行は、単に再実行することで復旧できます。
- 完了した実行は、検証パスとして繰り返すことができます。正しい結果とは、「追記なし」かつ「すべてが既に存在している」状態です。
- ターゲットで削除されたメッセージは、インデックスから消えるため、次の実行時に戻ってきます。

メッセージが既に存在するかどうかは、以下の順序で2つの基準によって決定されます：

1. **Message-ID**（正規化済み）。これが作業のほぼすべてを担います。
2. **フィンガープリント**。送信者、受信者、件名、および2秒以内の送信時間に基づきます。これは、保存されているMessage-IDが欠落しているか、不正な形式であるメッセージをカバーします。そのようなメッセージは元のMessage-IDで復元することができないため、この第2の基準がなければ、実行のたびに重複してしまいます。

ジョブは、フィンガープリントによる一致がいくつあったかを別途報告します。これは、フィンガープリントが静かに失敗する可能性がある基準だからです。

## ⚙️ Configuration {#configuration}

新しい `Offload` セクションが追加されます。デフォルト値は以前の動作を再現します：

```json
"Offload": {
  "MaxConcurrentJobs": 1,
  "PrefetchMaxMessages": 500000,
  "ExcludedSourceFolders": [],
  "FolderRenameMap": {},
  "MarkAsSeen": true
}
```

| Key | Default | Purpose |
|---|---|---|
| `MaxConcurrentJobs` | `1` | 同時に実行できるリストアまたはoffloadジョブの数。1に設定すると、ジョブキューが常に持っていた厳密なシリアル動作を維持します。この値に関わらず、1つのターゲットメールボックスにつき最大1つのジョブが実行されます。 |
| `PrefetchMaxMessages` | `500000` | ターゲットメールボックスからインデックス化されるメッセージ数の上限。これを超えると、重複チェックは単一のフォルダに絞り込まれ、その旨がログに記録されます。 |
| `ExcludedSourceFolders` | empty | オフロードしないソースフォルダ。リネーム前に照合され、サブフォルダも含まれます。 |
| `FolderRenameMap` | empty | ソースフォルダパスの先頭セグメントを書き換えます。 |
| `MarkAsSeen` | `true` | 追記されたメールに既読フラグを立てるかどうか。 |

両方のフォルダ設定は、意図的に空の状態で提供されます。リネームやフォルダの破棄を求められていないのにそれらを行うと、すでにリストアパスを使用しているユーザーを驚かせてしまうため、設定なしでの実行は、スパムフォルダを含めすべてを移行し、ターゲット自身の特殊フォルダの隣に2つ目の特殊フォルダセットを作成します。

### Folder exclusions and renaming {#folder-exclusions-and-renaming}

ExchangeからDovecotへの移行の場合、2つの設定は通常以下のようになります：

```json
"ExcludedSourceFolders": ["Junk E-Mail", "Deleted Items"],
"FolderRenameMap": {
  "Sent Items": "Sent",
  "Deleted Items": "Trash",
  "Junk E-Mail": "Junk"
}
```

リネームマップがない場合、Dovecotが独自のspecial-useフォルダを事前に作成するため、移行されたすべてのメールボックスには `Sent` と `Sent Items` の両方が存在することになります。

これらの適用方法について、驚かされる可能性がある4つの点を知っておく価値があります：

1. **Exclusions（除外）はソース名に対して最初に照合されます**。もしリネームが先に行われると、`Deleted Items` に対する除外設定は、それが `Trash` に変わった後では決して機能しません。
2. **Renaming（リネーム）は、セグメントの境界において、最も長く一致するパスプレフィックスを書き換えます**。`Sent Items` が `Sent` になると、`Sent Items/2019` も `Sent/2019` になり、`Sent Items Archive` はそのまま残ります。
3. **照合はケースインセンシティブ（大文字小文字を区別しない）**であり、`/` と `\` の両方がセパレータとしてカウントされます。
4. **2つのソースフォルダが1つのターゲットに集約されることがあります**。`Sent Items` と `Sent` が両方とも `Sent` になることは問題なく、ターゲットフォルダが二重に開かれることもありません。

2回の実行の間でリネームマップを変更しても、何も重複することはありません。重複チェックは、解決された単一のフォルダではなく、ターゲットメールボックス全体をカバーしているためです。

## 🖥️ Running it from the interface {#running-it-from-the-interface}

アカウントの詳細ページにある **Offload to Another Mailbox** を開くと、ターゲットメールボックス、ターゲットルートフォルダ、フォルダ構造を保持するかどうか、日付ウィンドウ、ドライランのスイッチ、および追記されたメールを既読にするかどうかのフォームが表示されます。設定済みの除外設定とリネームマップは読み取り専用で表示されるため、実行が予期せぬ結果になることはありません。

ジョブはキューに入れられ、その進捗とフォルダごとのレポートは、ジョブステータスページおよび **Jobs** の下に表示されます。フォルダごとのレポートにはソースフォルダ名が含まれるため、ジョブを開始したユーザーと管理者のみに表示されます。

ターゲットメールボックスは、本番稼働前に移行先を準備するために、無効化されたIMAPアカウントである場合があります。ターゲットに接続できない場合、実行はエラーとして報告されます。Microsoft 365アカウントはオフロードのターゲットにできません。Graphのリストアパスに変更はありません。

### Who may run it {#who-may-run-it}

管理者は任意の2つのアカウント間でオフロードを実行できます。セルフマネージャーは、**自身に割り当てられたアカウント間でのみ**オフロードを実行できます。これは両端において適用されます。ソースについては、アカウントページがすでにその範囲に限定されているためであり、ターゲットについては、ターゲットリストが同じセットに絞り込まれ、ジョブ開始時にリクエストが再度チェックされるためです。したがって、割り当てられたアカウントが1つしかないセルフマネージャーには、対象となるターゲットが存在しないため、その旨が通知されます。

スコープ（範囲）は、REST APIやMCPサーバーと同じリゾルバーである `IAccountAccessResolver` から取得されるため、「誰がどのメールボックスを使用できるか」の定義は一貫しています。決定自体は `OffloadTargetEligibility` にあり、ターゲットリストとリクエストチェックの両方がこれを呼び出すため、フォームが提示するものとサーバーが受け入れるものが乖離することはありません。

## ⌨️ Running it from the command line {#running-it-from-the-command-line}

```bash
docker compose exec mailarchive-app dotnet MailArchiver.dll \
  --offload --source-account-id 3 --target-account-id 7 \
  --since 2025-08-01 \
  [--until 2026-08-01] [--target-folder INBOX] \
  [--preserve-folders] [--dry-run] [--no-mark-seen]
```

| Argument | Meaning |
|---|---|
| `--source-account-id` | アーカイブ済みメールを読み取るアカウント。必須。 |
| `--target-account-id` | 追記先のIMAPアカウント。必須であり、ソースと異なっている必要があります。 |
| `--since` | 送信日の包含的な下限、`YYYY-MM-DD`。必須。 |
| `--until` | オプションの包含的な上限。 |
| `--target-folder` | ターゲットメールボックス内のルートフォルダ。デフォルトは `INBOX`。 |
| `--preserve-folders` | ルートの下にソースのフォルダ構造を再作成する。 |
| `--dry-run` | 何が起こるかを報告する（何も追記しない）。 |
| `--no-mark-seen` | Seenフラグを付けずに追記する。 |

Exit codes:

| Code | Meaning |
|---|---|
| `0` | すべてが追記されたか、あるいは既に存在していました。 |
| `1` | 少なくとも1つのメッセージが失敗したか、あるいは実行自体が失敗しました。 |
| `2` | 呼び出しが誤っています：引数の不正または不足、不明なアカウント、ターゲットがIMAPではない、ソースとターゲットが同一。 |

1回の呼び出しで1つのメールボックスを処理するため、ソース、ターゲット、カットオフを含むCSVから、大量のメールボックスをスクリプトで処理することが可能です。

> **Running several at once.** 「1ターゲットにつき1ジョブ」のルールは単一のプロセス内でのみ適用されます。したがって、*同じ*ターゲットメールボックスに対して2つのコマンドライン呼び出しを同時に行うと、一方が書き込みを開始する前にそれぞれが重複インデックスを取得してしまい、同じメールを両方が追記してしまう可能性があります。CSVの各行が異なるメールボックスであるという通常の場合のように、すべての同時実行が異なるターゲットを持つように作業を分割してください。

## 🗓️ How the cutoff is interpreted {#how-the-cutoff-is-interpreted}

- フィルターは**送信日**に対して適用され、メッセージがアーカイブされた時ではありません。アーカイブ時（archived-at）のタイムスタンプはアーカイブ実行時の時刻であり、カットオフには意味を持ちません。
- 「過去12ヶ月」のような相対的なウィンドウは、**ジョブが作成されたときに固定の日付に解決されます**。ジョブは長時間実行されたり、その後に繰り返されたりすることがあり、毎回同じメールを選択する必要があるため、相対的なウィンドウを保持すると時間が経過するにつれてズレが生じてしまいます。
- カットオフは、検索画面と同じ**設定された表示タイムゾーン**で解釈され、下限はその日の 00:00 からの包含的な値となります。上限はその日の全時間を包含します。相対的なウィンドウ（「過去Nヶ月」）も、`SentDate` の保存方法と同様に、その表示タイムゾーンで解決されます。

### Known limitation {#known-limitation}

- 重複インデックスが `Offload:PrefetchMaxMessages` に達した場合、単一のフォルダに対して再試行するのではなく、スコープが縮小され、その旨がログに記録されます。インデックスビルダーが提供する `restrictToFolder` フォールバックは、現在のところoffloadパスでは使用されていません。制限を引き上げることが推奨される対処法です。

## 📋 A migration, end to end {#a-migration-end-to-end}

1. ターゲットメールボックスを作成します。一度に多数作成する場合は、[Account Import](Account-Import.md) のCSV一括インポートを参照してください。
2. `Offload:ExcludedSourceFolders` と `Offload:FolderRenameMap` を設定します。両方ともデフォルトでは空であるため、これをスキップするとスパムフォルダも移行され、重複した特殊フォルダが作成されます。
3. オフロードする前に、各ソースメールボックスが完全にアーカイブされていることを確認します。
4. **すべてをドライランします。** 何かを書き込む前に、カウントと解決されたターゲットフォルダ名を確認してください。
5. 本番実行。まずは `MaxConcurrentJobs` を 2 にして開始し、ターゲットサーバーの負荷状況（DovecotはユーザーおよびIPごとに同時接続数を制限します）を確認してから数値を上げてください。
6. 検証のために実行を繰り返します。「追記なし」かつ「すべてが既に存在している」状態になることを期待してください。
7. ソースアカウントを無効にします。

スループットは `BatchOperation:PauseBetweenEmailsMs` によって制限されます。デフォルトは 50 ms であり、サーバーのレイテンシがカウントされる前に、最大で毎秒20回の追記が可能です。

## 🔍 What the counters mean {#what-the-counters-mean}

| Counter | Meaning |
|---|---|
| Appended | ターゲットに書き込まれたもの。ドライランの場合は、書き込まれる予定だったもの。 |
| Already present | いずれかの基準により、ターゲットに既に存在していたもの。 |
| of those by fingerprint | Message-IDではなく、第2の基準によって認識されたものの数。 |
| Excluded folder | ソースフォルダが除外設定されているためスキップされたもの。 |
| Failed | 追記できなかったもの。 |

重複インデックスがターゲットメールボックス全体をカバーしていない場合（`PrefetchMaxMessages` を超えた場合や、フォルダが読み込めなかった場合）、警告が報告されます。その状態では、繰り返し実行を行うと、インデックス化されなかった部分に既に存在するメールが追記される可能性があります。

## ⚠️ Notes and limits {#notes-and-limits}

- 復元されたメールは、メッセージの `Received` チェーンから取得された（または送信日にフォールバックされた）**元の配信時刻**をIMAP内部日付として保持するようになります。以前はアーカイブ実行時の時刻を保持していたため、サーバー側での到着順のソートや、ターゲットでの経過時間に基づくルールが壊れていました。
- 繰り返し実行は既に存在するものをスキップするため、誤った内部日付は再実行では修正できません（メッセージは認識され、スキップされます）。本番実行の前にこれを正しく設定するか、ターゲット上の影響を受けたメッセージを削除して再度実行してください。
- Microsoft 365 はオフロードのターゲットとしてサポートされていません。
- 重複検出は、ターゲットメールボックス内で「見える」ものしか認識できません。他のルートでターゲットに到達したメールは、2つの基準が偶然一致する場合にのみ捕捉されます。
