# 📊 Rate Limit Handling {#rate-limit-handling}

[← Back to Documentation Index](index.md)

## 📋 Overview {#overview}

Многие почтовые провайдеры накладывают ограничения на пропускную способность при доступе по IMAP. Эти лимиты обычно варьируются от нескольких сотен мегабайт до нескольких гигабайт за 24-часовой период. При синхронизации больших почтовых ящиков, превышающих эти лимиты, процесс синхронизации обычно завершается ошибкой или оказывается неполным.

Mail Archiver включает в себя встроенную систему обработки ограничений скорости, которая автоматически управляет этими ограничениями, обеспечивая надежную синхронизацию даже для больших почтовых ящиков.

## ⚙️ How It Works {#how-it-works}

### Automatic Bandwidth Tracking {#automatic-bandwidth-tracking}

Система постоянно отслеживает объем данных, загружаемых во время IMAP-синхронизации. Когда достигнут настроенный лимит пропускной способности:

1. **Sync Pauses Automatically**: Текущая операция синхронизации корректно останавливается.
2. **Progress is Saved**: Контрольные точки (checkpoints) сохраняют точное место, на котором остановилась синхронизация.
3. **Status Updates**: В панели управления у аккаунта отображается статус "Rate-Limited".
4. **Automatic Resume**: Когда лимит сбрасывается (обычно через 24 часа), синхронизация возобновляется с сохраненной контрольной точки.

### Example: 14 GB Mailbox with 2.5 GB Daily Limit {#example-14-gb-mailbox-with-25-gb-daily-limit}

```
Day 1:  Sync starts → ~2.5 GB downloaded → Rate-Limited
        Status: Rate-Limited, Checkpoint saved

Day 2:  Limit still active → Sync skipped

Day 3:  Limit resets → Sync resumes from checkpoint
        → Additional ~2.5 GB → Rate-Limited again

Day 4-6: Continues...

Day N:   All 14 GB synced → Status: Completed
```

## 🔧 Configuration {#configuration}

### Enabling Bandwidth Tracking {#enabling-bandwidth-tracking}

Добавьте следующий раздел в ваш `appsettings.json`:

```json
{
  "BandwidthTracking": {
    "Enabled": true,
    "DailyLimitMb": 2500,
    "WarningThresholdPercent": 80,
    "PauseHoursOnLimit": 24
  }
}
```

### Configuration Options {#configuration-options}

| Option | Description | Default | Example |
|--------|-------------|---------|---------|
| `Enabled` | Включить/выключить отслеживание пропускной способности | `false` | `true` |
| `DailyLimitMb` | Ежедневный лимит загрузки в мегабайтах | `2500` | `2500` |
| `WarningThresholdPercent` | Процент лимита для вывода предупреждений в логи | `80` | `80` |
| `PauseHoursOnLimit` | Количество часов паузы при достижении лимита | `24` | `24` |

### Setting the Correct Limit {#setting-the-correct-limit}

Чтобы определить подходящее значение `DailyLimitMb`:

1. Изучите документацию или условия обслуживания вашего почтового провайдера.
2. Ищите информацию об ограничениях пропускной способности IMAP или квотах на загрузку.
3. Свяжитесь с вашим системным администратором, если вы используете корпоративную почтовую систему.
4. Начните с консервативного значения, если не уверены (например, 2000 MB).
5. Отслеживайте логи на наличие предупреждений о лимитах скорости во время начальных синхронизаций.

## 👤 User Experience {#user-experience}

### Dashboard Indicators {#dashboard-indicators}

Когда ограничение скорости активно, аккаунт отображает:

- **Status**: "Rate-Limited" 
- **Info Banner**: Объясняет ситуацию и примерное время сброса лимита.
- **Sync Progress**: Показывает количество обработанных писем до достижения лимита.

### Automatic Behavior {#automatic-behavior}

1. **No Manual Intervention Required**: Система делает все автоматически.
2. **Application Restarts**: Если приложение перезапускается, состояние ограничения скорости сохраняется в базе данных.
3. **Multiple Accounts**: Каждый аккаунт отслеживает свою пропускную способность независимо.

### What Gets Saved {#what-gets-saved}

При возникновении ограничения скорости система сохраняет:

- **Sync Checkpoints**: Точное положение в каждой папке, где остановилась синхронизация.
- **Bandwidth Usage**: Общее количество загруженных байт за текущие сутки.
- **Limit State**: Достигнут ли лимит и когда он будет сброшен.

## 🗄️ Database Maintenance {#database-maintenance}

`DatabaseMaintenanceService` автоматически очищает старые данные:

- **Bandwidth Records**: Удаляются через 7 дней.
- **Sync Checkpoints**: Завершенные контрольные точки удаляются через 30 дней.
- **Incomplete Checkpoints**: Сохраняются до завершения синхронизации.

## ✅ Best Practices {#best-practices}

### For Large Mailboxes {#for-large-mailboxes}

1. **Enable Bandwidth Tracking**: Необходимо для почтовых ящиков, размер которых превышает ежедневный лимит.
2. **Plan for Initial Sync**: Полная синхронизация большого почтового ящика может занять несколько дней.
3. **Monitor Progress**: Проверяйте статус ограничения скорости в панели управления.
4. **Don't Interrupt**: Позвольте автоматическому возобновлению завершить процесс.

### For Administrators {#for-administrators}

1. **Set Appropriate Limits**: Приведите `DailyLimitMb` в соответствие с фактическими лимитами вашего почтового провайдера.
2. **Monitor Logs**: Предупреждающие сообщения появляются при достижении 80% лимита.
3. **Database Space**: Отслеживание пропускной способности использует минимальный дополнительный объем хранилища.
4. **Backup Before Changes**: Всегда делайте резервную копию перед изменением настроек ограничения скорости.

### Performance Considerations {#performance-considerations}

- ✅ **Memory Impact**: Ничтожно мало — отслеживаются только байты, письма не хранятся в памяти.
- ✅ **Database Impact**: Минимально — небольшие записи очищаются автоматически.
- ✅ **Sync Speed**: Никакого влияния на производительность во время активной синхронизации.

## 🛡️ Transient FETCH Errors / Server-Side Throttling {#transient-fetch-errors-server-side-throttling}

В дополнение к описанному выше отслеживанию пропускной способности на основе байтов, Mail Archiver также обнаруживает и реагирует на **throttling (ограничение частоты запросов) для отдельных сообщений**, сигнализируемый самим IMAP-сервером. Некоторые хостинговые IMAP-провайдеры применяют ограничение для аккаунта или IP, которое **не зависит от настроенных пауз `BatchOperation`**, так как ограничение применяется на стороне сервера на основе общего объема запросов в течение текущей сессии.

### Symptoms {#symptoms}

Сервер возвращает ответ `NO` (или `BAD`) на одиночную команду `FETCH` для тела сообщения с такими сообщениями, как:

- `NO Service temporarily unavailable`
- `NO Server unavailable, try again later`
- `NO [LIMIT] ...`
- `NO [OVERQUOTA] ...`
- `NO [UNAVAILABLE] ...`
- `NO [INUSE] ...`
- ответы, содержащие `throttle`, `rate limit` или аналогичные маркеры

Аутентификация, просмотр списка папок и сам поиск сообщений обычно по-прежнему проходят успешно — не удается получить только полное содержимое сообщения.

### Automatic Handling {#automatic-handling}

При обнаружении такой временной ошибки Mail Archiver применяет стратегию повторных попыток для каждого сообщения:

1. **Retry with exponential backoff**: До **3 попыток** для одного и того же сообщения с задержками **5 с → 15 с → 60 с**.
2. **Connection recovery**: Перед каждой попыткой состояние соединения, аутентификации и выбора папки проверяется и, при необходимости, восстанавливается.
3. **Reset on success**: Успешный FETCH сбрасывает счетчик последовательных неудачных попыток.
4. **Graceful sync pause**: Если после всех попыток **10 сообщений подряд** по-прежнему возвращают временные ошибки, текущий сеанс синхронизации корректно приостанавливается — по тому же механизму, что и при достижении лимита пропускной способности:
   - Метка времени `LastSync` **не** обновляется.
   - Если включен `BandwidthTracking`, контрольные точки сохраняются, чтобы следующий запуск синхронизации возобновился с последнего успешно обработанного сообщения.
   - Задача помечается как ограниченная по скорости (rate-limited).
   - Следующая запланированная синхронизация начнется автоматически.

### Mitigation {#mitigation}

Если вы регулярно сталкиваетесь с ограничением на стороне сервера, снизьте частоту запросов, настроив `BatchOperation`:

```yaml
BatchOperation__BatchSize=10
BatchOperation__PauseBetweenEmailsMs=500
BatchOperation__PauseBetweenBatchesMs=5000
```

Обратите внимание, что некоторые провайдеры ограничивают скорость на основе **общего объема байт** или **общего количества FETCH за временное окно**, а не на основе количества запросов в секунду. В таких случаях:

- Включите `BandwidthTracking` (см. выше) и настройте `DailyLimitMb` в соответствии с документацией провайдера. Синхронизация будет корректно приостанавливаться при исчерпании ежедневного бюджета и автоматически возобновляться на следующий день.
- Начальная синхронизация очень больших почтовых ящиков может занять несколько дней, что является ожидаемым поведением.

### What Counts as a Transient Error {#what-counts-as-a-transient-error}

Только ответы IMAP `NO`/`BAD` с текстом или кодами ответов, связанными с ограничением скорости, считаются временными. Другие ошибки (некорректные сообщения, проблемы с декодированием UTF-8 и т. д.) по-прежнему считаются `FailedEmails` немедленно и **не** запускают логику повторных попыток/паузы.
